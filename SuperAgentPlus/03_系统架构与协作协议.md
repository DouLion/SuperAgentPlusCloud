# 系统架构、领域对象与协作协议

> 设计提案 v0.3。命令、字段与部署形态均为设计约定，不是现成 API 或已验证的 CLI 能力。不提供系统实现。  
> v0.3 修正：G2 独立验收任务，G3 总工只看方向简报；总工不读实现现场。见 [总工信息隔离](07_总工信息隔离.md)。

## 1. 架构总览：四个面，一条权威状态链

| 面 | 组成 | 信任与职责边界 |
|---|---|---|
| 交互与协作面 | Web/CLI/消息入口、讨论文档、画板、初审/验收/方向简报工作台 | 接收意图、展示版本、收集人的判断；原始内容默认不是可执行授权 |
| 项目控制面 | 身份/委派、政策、契约、决策、任务、状态机、租约、验收/方向裁决编排、审计、事件发送 | 确定性控制正式状态；不运行项目中的任意代码，不替人做 G1/G2/G3 |
| 分布式执行面 | 人类、Agent、异构适配器、受限执行环境 | 只获得任务范围的上下文与短期权限；不能自行验收或做方向裁决 |
| 验证与交付面 | 可信验证、G2 独立验收、G3 方向简报/裁决、集成队列、发布授权、结果观察 | 以实际候选与组合版本为对象；验收/发布凭据与执行凭据分离 |

**逻辑中心化的是项目规约与提交顺序，不是所有思考，也不是所有审批。** 可以有多个模型、多个入口和服务副本，但某个项目的关键事实不能由多个断开的控制节点同时各自裁定。**G1 由 CLI 操作者完成，G2 由独立验收人完成，G3 由总工完成；中心服务器只提供验权、记录、分派、简报编排和按规则汇总。**

系统总览见 [可探索架构图][arch-html]；普通任务与结构变更的门禁路径见 [协作闭环图][flow-html]。图展示设计级责任和流转，不是物理部署图。

### 1.1 承载清单（服务器 / 终端 / 工程设施）

| 承载位置 | 承载内容 | 不承载 |
|---|---|---|
| 中心服务器 | 意图接收与组织、契约/决策登记、任务池、认领与租约、上下文协调、G1 校验、G2 验收编排、G3 方向简报/裁决编排、权威状态与审计、Outbox、与工程设施的受控对接 | 不运行项目任意代码；不替操作者初审；不替验收人验收；不替总工做方向裁决；不持有发布凭据 |
| 人类终端 A（CLI 操作者） | **任一接入的 CLI 会话都可发起意图**；CLI/IDE/Agent 执行、自测、候选形成、操作者查看与初审签署、正式提交 | 不能由 Agent 代签初审；不能在无有效租约时推进正式状态 |
| 人类终端 B…N（验收人/总工） | G2 独立验收；G3 方向/结构/里程碑裁决（只看方向简报）；也可发起、认领、执行和初审自己的成果 | 总工不读 bug 日志/diff；G2 不能由执行者兼任；G3 不因职务自动成立 |
| 受控工程设施 | 仓库、可信 CI、制品库、部署环境、实际运行与观测 | 不负责人类签署；不被中心服务器当作可任意改写的内部存储 |

**G1 在人类终端 A；G2/G3 在人类终端 B…N；服务器只校验身份、版本、证据与规则，编排简报并记录结果。** 总工与验收人不是服务器里的“AI 角色”。

## 2. 推荐组件边界

| 组件 | 接受输入 | 产生输出 | 明确不做 |
|---|---|---|---|
| Intake Gateway | 认证来源的消息、Issue、CLI 意图 | 原始意图、来源引用、去重关联 | 不把群聊里的每句话自动作为已授权任务 |
| Planning Assistant | 有权限的上下文、目标、意图 | 澄清问题、分级/拆分/影响建议 | 不直接批准结构决策或人类 G2/G3 |
| Policy & Identity | 身份、委派、项目章程、资源规则 | 有限授权、门禁判断及原因 | 不以模型提示词代替权限控制 |
| Contract & Decision Registry | 受控草案、人的确认、变更提案 | 不可变版本、有效指针、失效屏障 | 不静默覆盖执行中的标准 |
| Task Coordinator | 合法契约、依赖、认领命令、容量 | 正式任务、租约、尝试、状态事件 | 不把调度成功当作任务成功 |
| Context Service | 任务、访问范围、当前有效引用 | 有来源的最小上下文包、版本摘要 | 不上传全项目私密会话或把摘要当作原始事实 |
| Execution Adapter | 有限工作授权、上下文、协作消息 | 心跳、进展、候选产物、证据声明 | 不持有人类初审/验收/方向裁决签署或生产发布令牌 |
| Verification Gateway | 候选引用、契约、证据策略 | 可信复验、证据绑定与缺口 | 不单靠 Worker 自报日志放行 |
| Operator Primary Gate | 候选、证据清单、操作者身份 | 初审确认或退回、正式提交请求 | 只确认“可以提交”，不代替 G2/G3 |
| Independent Acceptance (G2) | 完整候选、证据、契约 | 任务验收 ACCEPTED / REWORK | 不以总工方向同意替代任务验收 |
| Information Gate / Direction Brief | 请求、证据指针、方向包 | 一页式方向简报；按需 detail pack | 不把日志/diff/复现放进简报；不替总工决定 |
| Chief Direction Gate (G3) | 方向简报、方向包、授权总工身份 | 方向/结构/里程碑裁决、例外 | 不逐任务看实现；不提供“全体自动通过” |
| Integration & Release | 已 G2 验收候选、目标基线、发布授权 | 组合验证、集成记录、发布观察 | 不以子任务绿色替代组合验证 |
| Audit & Event Delivery | 同事务的事实与待发送记录 | 可追溯事件、看板/通知投影 | 不作为自动客观绩效系统 |

这些是职责模块，不要求第一版做成十余项微服务。**推荐先做模块化单体控制面 + 分离的执行/验证环境**，用清晰接口保留未来拆分能力。

“Operator Primary Gate”“Independent Acceptance”“Chief Direction Gate”是**人类终端上的工作界面/席位**，不是服务器里的“AI 角色”。服务器替它们校验身份、版本、证据与规则，并持久化人的签署；信息闸门负责把操作现场压成方向简报。

## 3. 领域对象：从目的到结果

| 对象 | 最小含义与关键关联 |
|---|---|
| Project Charter | 项目目的、权限、风险规则、G2/G3 独立性、讨论法定人数、预算与数据边界 |
| Goal | 期望结果、基线、指标、观察窗口、目标责任人；可关联多个意图与协作组 |
| Intent | 原始请求、提出者、来源、澄清状态；可以被否定、合并或转为诊断 |
| Proposal / Discussion | 需要决策的问题、选项、参与者、异议、结论草案；不等于已生效决策 |
| Decision Version | 选择、范围、理由、假设、批准人、有效性；被契约明确引用 |
| Contract Version | 目的、范围、非目标、验收、证据、风险、权限、基线、预算与责任 |
| Work Package | 可整体验收的协作结果，含任务依赖、接口与集成责任人 |
| Task | 按契约推进的正式工作；当前 revision、交付状态与 HOLD 原因 |
| Attempt / Lease | 一次执行身份与有时限的正式执行权；关联责任人、Agent、Runtime |
| Artifact / Evidence | 具体候选产物与可复核材料；摘要、来源、环境、策略、生成者 |
| Primary Attestation | 操作者对精确候选的人工初审签署；绑定契约、候选、证据快照与签署人 |
| Acceptance (G2) | 独立验收人对完整候选/证据的任务级结论；绑定契约、候选、证据与验收规则 |
| Direction Brief | 信息闸门生成的一页方向简报；问题、选项、影响、风险、证据指针、建议 |
| Direction Policy | 授权总工名单、通过条件、必需职责、否决规则、僵局与联合方向裁决规则版本 |
| Direction Decision (G3) | 总工对方向/结构/里程碑的裁决；绑定 brief/方向包版本，不含实现细节 |
| Appeal | 精确对象的人类裁决争议与纠正；不覆盖旧提交 |
| Integration Record | 合入哪一目标基线、组合候选、验证和冲突处理 |
| Release / Observation | 哪个版本部署到哪个环境；何时观察到何种业务结果 |
| Participation / Grant | 提出、监督、实现、审查、集成等参与关系，以及被授予的权限 |

上述为逻辑模型，不意味着要创建一张图数据库或“一对象一服务”。第一版可用事务数据库里的关系与引用；复杂检索可以后续建立图投影。

### 3.1 三种事实来源

- **协作事实**：由控制面管理，例如契约、有效决策、认领、人的裁决。
- **工程事实**：由仓库、CI、制品库、部署系统提供，例如 commit、构建、测试与实际部署版本。
- **业务事实**：由目标的真实观测来源提供，例如用户场景、性能测量、事故、人工判断。

中央数据库不能替代工程与业务事实。它维护关联、授权与解释；外部系统回调也必须验证身份、对象和时效，不因收到 webhook 就认定任务已完成。

## 4. 权威存储与一致性

### 4.1 推荐的第一版持久化模式

采用**当前状态表 + 不可变版本/审计记录 + 事务性待发送事件（Outbox）**。一次正式状态变更应在同一事务里完成：

授权/版本/租约检查 → 更新当前状态 → 记录事实事件/审计 → 写入待发送记录 → 提交。

事务提交后才发送通知。通知失败可重发，看板滞后不影响权威判断。此模式可以拥有可追溯事件，但**不等于完整事件溯源**；是否让所有状态只由事件重放生成，是后续成本与维护取舍。

- 单机验证可用服务端本地 SQLite；不把数据库放共享网络盘供各 CLI 直接写。
- 跨机 Worker 只访问控制服务，不直连修改权威表。
- 小团队持续使用可选具备合适事务与备份能力的数据库；不预先规定品牌。
- 代码与大型制品留在仓库/制品存储，权威表保存摘要、来源与访问引用。
- 不将完整提示词、代码、日志和敏感凭据全部塞进事件流。

### 4.2 强一致与最终一致的划分

| 关键强约束 | 允许最终一致的投影 |
|---|---|
| 同一任务的认领、租约、状态推进 | 任务看板、搜索、通知摘要 |
| 决策/契约有效性与验收/集成的并发顺序 | 推荐排序、历史统计 |
| 角色授权、失效委派与关键门禁 | 能力展示、非权威在线指示 |
| 精确候选的验收与重复裁决去重 | 文档摘要、上下文索引 |

每个命令携带期望 revision。内核在一个权威事务边界内同时检查相关任务 revision、契约、决策有效性和授权。不能先检查决策“有效”，再在另一个不受保护步骤里通过验收。

每个项目可有 `governance_generation`：影响执行/验收的治理变更推进该代次。精细依赖成熟后可仅失效相关范围；MVP 可以保守地暂停该项目尚未完成的相关执行与裁决，宁可多复核，不可静默漏失效。

### 4.3 高可用与恢复

控制 API 可以多副本，关键写入仍通过同一权威事务机制。主写入失去明确权威时，不做新的认领、裁决或发布；读缓存和本地草稿可继续。第一版不做断网双活、多主写入或跨地域任意冲突合并。

恢复必须涵盖：当前租约、未发送事件、待验证产物、未知外部副作用、权限撤销与备份来源。备份回退可能使递增序号回退，因此恢复后要切换 `authority_epoch` 或等效新权威代次，拒绝旧权威期间签发的令牌。

“数据库能恢复”不等于“外部已经发生的发布/付款也被恢复”。外部事实需查询与核对，不能仅靠重放命令。

## 5. 设计级协议：命令与事件分开

传输可以采用 HTTP/RPC、流订阅或工具桥接。**MCP/A2A 可以承载交互，但不会自动给出本系统的原子认领、租约、幂等、版本、问责、G1/G2/G3 语义。** 这些语义由本节定义，再映射到实际工具能力。

### 5.1 命令公共信封

| 字段 | 用途 |
|---|---|
| protocol_version | 语义版本及兼容协商 |
| project_id | 权威、权限、检索与制品的隔离作用域 |
| command_id / idempotency_key | 持久化识别同一操作；重试不重复生效 |
| actor_id / actor_type | 谁提出命令；服务端根据认证绑定，不能信任客户端自填 |
| runtime_id / grant_id | 哪个运行实例、基于哪次委派 |
| accountable_human_id | 关联执行责任，服务端验证是否符合授权链 |
| target_id / expected_revision | 操作哪个对象；防止旧状态覆盖新状态 |
| correlation_id / causation_id | 串联意图、任务、尝试、证据与裁决 |
| payload_digest | 检测同幂等键却提交不同载荷的冲突 |
| client_observed_at | 辅助诊断；不决定权威顺序或租约期限 |

服务端返回：命令是否已提交、结果引用、当前 revision、权威记录时间、错误类型/解除条件。同键同载荷返回原结果；同键异载荷返回冲突。客户端超时代表**结果未知**，先查询命令结果，再决定重试。

### 5.2 关键命令与前置条件

| 命令（设计名称） | 前置条件 | 结果/限制 |
|---|---|---|
| RegisterRuntime | 已授权身份、能力清单、协议兼容 | 注册运行实例；注册本身不获得任务、G1/G2/G3 权限 |
| CreateIntent | 项目成员/受限来源的发起权限 | 保存原意图；不是直接启动执行 |
| PublishContract | 契约完整；结构提案有有效批准 | 产生不可变版本与可准备任务 |
| ClaimTask | READY/可返工；无 HOLD；依赖、授权、容量成立；期望 revision 一致 | 原子签发 lease、attempt 与隔离令牌 |
| RenewLease | 同一 Runtime/Attempt；原租约未到期、未关闭/撤销；epoch/token、grant 与执行授权有效 | 以服务器时间续租；过期不能复活旧租约；不得无限续租绕过预算 |
| ReportProgress | 授权尝试 | 记录观察性进展；不能直接修改任务交付状态 |
| ConfirmPrimaryAttestation | 真实人类认证；该候选的操作者/监督身份；契约与证据快照有效 | 生成初审签署；只表示“可以提交”，不推进 ACCEPTED |
| ApproveAndSubmitCandidate | 有效租约、契约/决策、无相应 HOLD；**本人有效初审签署**；证据准入成立 | 同事务固定候选、记录初审、关闭该尝试执行权并建立 G2 验收 |
| RecordAcceptance | 授权验收人的人类身份；G2 验收开放；同一候选/契约/证据快照；规则版本一致 | 记录 G2 通过/整改；通过 → ACCEPTED，不推进集成 |
| IssueDirectionBrief | 请求/证据指针/方向包齐备；闸门生成；不替总工决定 | 生成一页 `brief`；绑定请求、方向包、选项与证据指针 |
| RecordDirectionDecision | 授权总工；brief 与方向包版本一致；规则满足 | G3 方向/结构/里程碑裁决；不改变任务 ACCEPTED 状态 |
| SubmitCandidate（草案路径） | 当前契约/决策/租约有效；无相应 HOLD | 仅登记**未初审**的候选草案或迟到成果，进入隔离区，不能进入 G2 |
| ChallengeDecision | 具备提案权，提供影响/证据 | 建立挑战与风险 HOLD；不自动替换决策 |
| ActivateDecision / SupersedeDecision | 人类批准、职责覆盖、期望治理代次一致 | 先更新有效性/失效屏障，再发事件 |
| RequestIntegration | 已 G2 验收的精确候选，目标基线有效 | 排入集成队列，重新组合验证 |
| AuthorizeRelease | 发布人权限、指定集成对象/环境、风险与回滚成立 | 有限发布授权，不向普通 Worker 提供发布凭据 |
| ObserveExternalOperation | 已登记 operation，可信查询/回调 | 记录实际外部事实；不猜测超时结果 |
| CancelTask / RevokeGrant | 有权人/到期政策；核对副作用 | 停止正式权利，记录原因；不承诺杀死断网进程 |

字段表达的是控制协议，不建议开放“PUT 任意任务状态 = done”式接口。**没有 `ConfirmPrimaryAttestation` 的 `ApproveAndSubmitCandidate` 必须失败；没有有效 `RecordAcceptance` 的任何客户端请求都不能把任务写成 ACCEPTED；`RecordDirectionDecision` 不能替代 G2 验收。**

### 5.3 事实事件

示例事件：IntentCreated、ContractPublished、TaskClaimed、ProgressReported、PrimaryAttested、CandidateSubmitted、PrimaryAttestationWithdrawn、AcceptanceRecorded、AcceptanceConcluded、DirectionBriefIssued、DirectionDecisionRecorded、DirectionDecisionRejected、LeaseExpired、DecisionChallenged、DecisionSuperseded、IntegrationCompleted、ReleaseObserved、OutcomeMeasured。

事实事件包括：`event_id`、`project_id`、对象与 revision、服务器记录时间、操作者/委派引用、因果关联、对象摘要。事件只声明已经提交的事实，不能夹带自动获得权力的自然语言命令。

投递按**至少一次**设计：Outbox 重发，消费者按 event_id 去重；同对象按 revision 检测乱序/缺口，通过快照或事件游标补齐。跨对象不假设有一个客户端时钟定义的全局严格顺序。

## 6. 原子认领、租约与隔离令牌

### 6.1 认领不是先查再写

ClaimTask 必须在一个事务里同时验证：任务状态和 revision、有效契约、依赖门槛、授权与责任人、无有效租约、预算/容量。成功后同时记录：

`attempt_id`、`lease_id`、`lease_expires_at`、`authority_epoch`、单调递增 `fencing_token`、当前任务/契约/决策绑定。

并发两人只能有一方获得同一正式执行槽。另一方收到冲突与最新状态，可以邀请协作或认领其他子任务，而不是自行继续同一正式尝试。

### 6.2 租约解决权利，不保证物理停止

租约由服务器时间裁决，心跳只说明连接状态。续租同时检查原租约尚未到期、未关闭/撤销、属于同一 Runtime/Attempt，以及 grant、预算、风险与执行授权；执行 HOLD 阻断续租。过期后不能复活旧租约，只能经恢复核对后重新认领。到期后旧进程可能继续写自己的工作副本，因此必须使用 **fencing token（隔离令牌）**，并与到期/撤销检查结合：

- 正式提交与受控资源写入同时检查当前 epoch/token、租约期限/关闭状态、grant 有效性与该动作的 HOLD/授权条件，或使用等效即时退权机制。观察性迟到进度可以单独保留，不因此恢复写权。
- 新认领得到更高 token；旧 token 的正式动作被拒绝。尚未重认领时，旧 token 即使仍是最大值，过期租约也不能执行受控写入。
- 本地旧候选可隔离保存并显式复用，但不能恢复旧写权；正式提交已关闭的租约也不能继续续租或改写候选。
- 外部资源若只能比较 fencing、不能验证期限/撤销，不承诺到期立即停止副作用；无完整控制、幂等或结果查询能力时，不自动接管/重试，必须人工核对或禁止该副作用。

仅给 Worker 一个“过期时间”并让它自觉停下，不能保障正确性。也不承诺整个任意代码执行 exactly-once。

### 6.3 离线降级

- 可看已授权缓存、保留草稿、完成本地候选和诊断记录。
- 不可离线续租、认领、批准、正式推进任务、集成或发布。
- 到期后不得继续发起受控外部副作用；如果外部动作不可约束，则此任务不允许自动离线执行。
- 重连先核对 authority、attempt、lease、契约和决策；再按当前版本补证/导入。
- 长时间失联触发 HOLD 与责任人通知，不直接归类为低绩效。

## 7. 异构 CLI 适配：统一语义，不伪装统一能力

### 7.1 三种接入等级

| 等级 | 使用方式 | 适合情形 | 已知缺口 |
|---|---|---|---|
| A：人工桥接 | 人读取契约，在自己工具中执行，再经正式入口提交 | 任何工具、设计验证阶段 | 不能自动取消、监控或恢复；证据需独立复核 |
| B：协议参与者 | 工具/桥接读取任务、认领、接收上下文、报告状态 | 可调用标准接口的工具 | 不保证生命周期托管、沙箱或后台存活 |
| C：受控执行器 | 独立托管适配器管理 attempt、租约、进程、权限与产物 | 能可靠管理运行实例的工具 | 仍不能替代 G1/G2/G3；取消能力与副作用隔离须实测 |

DSH、OpenCode、其他 CLI 都是候选，不指定它们必然属于某个等级。支持某个协议、安装了插件或连接了 MCP Server，**不等于已具备 C 级能力**。

### 7.2 能力清单与降级

登记：工具/版本、支持动作、交互模式、恢复/取消、结构化回报、文件/网络隔离、制品导出、数据驻留、资源上限与已验证限制。

调度先按硬约束筛选，再推荐：

1. 权限、数据和运行环境是否允许。
2. 能否满足该任务的副作用控制和证据要求。
3. 需要人陪同还是可受控后台执行。
4. 是否有容量、预算与相关能力。

缺少强隔离或可查询副作用能力的节点，只接收相应低风险任务。连接失败不能降级为“给 CLI 发一段提示词然后认为完成”。

### 7.3 分布式协作协议不是模型调用协议

模型供应商、模型 API、CLI 会话协议和项目协作协议分属不同层。控制面不需要统一所有模型调用方式，只需要统一正式工作契约、状态与证据的提交语义。保留工具差异，比假装完全一致更可维护。

## 8. 上下文包与项目记忆

上下文包建议包含：

- 任务目的、非目标、验收条目、风险和停止条件。
- 不可变契约 hash/version、有效决策引用、治理代次。
- 指定仓库基线、相关接口/设计引用、已知依赖与冲突。
- 上次驳回的事实及响应清单，来源与访问权限。
- 允许的工具/数据/外部动作，预算与升级联系人。

摘要、检索结果和模型推断显式标注出处/状态；争议意见不能作为有效决策注入。合同正文和政策有分层优先级，任何附件自然语言不能覆盖硬性权限。

上下文更新用变更事件与确认，而不是“强行塞入更多聊天记录”。正式提交时再核对版本，即使节点没有收到更新也不会误放行。

长期记忆记录“当前为何这样做、何时应复核”，不是把私人会话永久存档。权限变更后检索与缓存也要受撤销策略约束；敏感内容不要因为进入摘要而获得更宽权限。

## 9. 可信证据、验收对象与集成

### 9.1 证据等级不是成功分数

| 证据来源 | 可以如何使用 |
|---|---|
| Worker 自报 | 声明与辅助定位；不能单独证明实际测试通过 |
| 有身份的独立人员复核 | 文档、分析、演示等可人工验证；记录方法和局限 |
| 受控 CI/验证环境 | 对具体候选与策略的复验；验证执行代码仍应在受限环境中 |
| 外部业务/部署观测 | 判断真实环境状态；需要对象关联、身份与采样条件 |

每项证据绑定：契约版本、候选 commit/内容摘要、验证策略与版本、测试集来源、环境/依赖版本、运行身份、时间、原始引用与结果。签名只证明来源与完整性，不证明内容一定真实。

不能只复跑 Worker 自己写的一套总会通过的测试。关键验收测试/策略由可信来源控制；修改它们需相应风险审查。验证签名密钥和发布凭据放在执行代码不能读取的边界外。

### 9.2 候选对象与简报对象必须一致

G1/G2 必须绑定当前契约与精确候选；候选内容、验收标准或依赖有效性变化，会使相关初审与 G2 不能继续放行，需要重新比对、复验和人的确认。

G3 必须绑定当前 `brief_id`、方向包版本与选项；方向包或简报变化后，旧 G3 意见不能自动沿用。G3 的输入不含实现细节；需要细节时走 scoped detail pack，且 detail 不合并回总工主上下文。

G2 通过后、集成前若基线变化，仍需组合验证；原 G2 事实保留，但不能当成组合版本已通过。集成产生的新组合版本不是原候选的同义词：原任务验收事实可以保留，但不能把它当成组合版本已验证。集成队列必须在真实目标基线上创建组合候选，检查编译、接口、迁移、业务关键路径与回归。

### 9.3 发布与观察

发布绑定集成对象、环境、授权人、操作 ID、风险窗口、回滚/补偿与实际观测。普通 Worker 不持有生产发布凭据。

部署超时不盲目重试：查询 operation_id 或目标实际版本；无法查询时进入人工核对。回滚可能涉及不可逆数据改变，因此“有旧代码版本”不是完整回滚方案。

紧急动作也有明确的人类授权身份与作用域，可以使用预定义事故政策缩短讨论，但不免除记录、风险边界与后续核对，不用 break-glass 变成永久权限。

## 10. 安全与治理威胁模型

| 风险 | 约束 |
|---|---|
| 提示注入：需求、代码、日志、驳回文本要求泄密/扩权 | 不可信内容始终作为数据；权限由内核/运行隔离执行，不由 Prompt 决定 |
| Agent 冒充人的 G1/G2/G3 | 三类签署都采用独立人类认证与显式确认路径；Agent grant 不可调用，凭据不下发到运行环境 |
| 初审被跳过或被自动化 | 没有有效 `ConfirmPrimaryAttestation`，提交命令失败；初审签署不能被 Agent 代签或补签 |
| G2 被总工方向同意替代 | 任务 ACCEPTED 只能由 `RecordAcceptance` 产生；G3 不改变任务状态 |
| 总工被操作细节污染 | 总工只读方向简报；日志/diff 默认不进上下文；detail pack 有 purpose/TTL，不合并回主上下文 |
| 联合方向裁决被拼票或凑数 | 意见绑定同一 brief/方向包/选项版本；缺席不计同意；名单变更需新规则版本 |
| 同一人既执行又验收/裁决 | 记录身份并按章程决定是否允许；G2 必须不同于执行者；G3 自审需显式标记/回避 |
| 同机人类凭据被执行代码读取 | 隔离凭据/会话/签名边界；不能因命令名叫 approve 就宣称只有人可用 |
| 跨项目检索与制品泄露 | project_id 作用域、来源授权、检索与下载逐次验证；摘要不放宽访问 |
| Worktree 被误当安全沙箱 | 额外约束文件系统、网络、凭据、CPU/费用；工作副本隔离与安全隔离分开设计 |
| 伪造证据或测试绕过 | 校验对象绑定，独立验证，可信策略与测试源，签名者在隔离外 |
| 授权过宽、无限代理链 | 短期、任务/attempt/动作/资源限定的 grant；转委派只能收窄，支持撤销 |
| 失控重试或高成本模型 | 预算、并发、超时、观察性进度、人工升级，不无限自我调用 |
| 审核/贡献数据被滥用 | 最小化、目的与保留期限、访问控制、纠错与申诉；绩效扩展默认关闭 |
| 管理员改审计/恢复旧记录 | 明确特权边界、备份与操作记录；必要时外部可信锚点/不可变存储增强篡改检测 |

人类显式认证是可审计的责任表达，不是证明“生物学上的人亲自完成了所有思考”。系统只能约束技术权限和记录判断依据，不能保证授权人永不滥用账号。

## 11. 审计、隐私与可观测性

### 11.1 可追溯，不夸大不可篡改

记录意图、批准、责任转交、正式尝试、证据、初审签署、G2 验收、G3 方向裁决、集成、发布与纠正关系。哈希链或签名可增强某些篡改检测，但没有可信外部锚点、密钥隔离和权限控制时，管理员可能连记录与校验材料一起改变。

不需要区块链作为第一版前提。数据保留、删除和隐私合规需设计：事件尽量只保存引用/摘要，敏感原文在有期限的独立存储；更正用关联记录表达，必要的合法删除保留最小合法审计信息。具体期限由项目/组织与法规确定。

### 11.2 优先观察系统瓶颈

关注：意图澄清时间、待初审/待 G2/待 G3 队列、无验收人/无总工任务数、执行/初审/验收/方向裁决/集成队列时长、契约变化率、按原因返工、失联与迟到提交、版本失效拦截、证据缺口、组合回归、目标结果、总工上下文污染事件。

日志关联到 project/task/attempt/command，而不把私人输入和密钥作为调试便利全部记录。告警需要可行动原因与处理人，不能只有“AI 异常”的红灯。

## 12. 设计决策与暂不决策

| 建议固定的原则 | 保持开放的实现选择 |
|---|---|
| 控制面不运行项目任意代码 | 后端语言、框架、数据库品牌 |
| 权威提交、版本、原子认领、幂等、失效屏障前置 | HTTP/RPC/MCP/A2A 的实际映射 |
| 人类 G1/G2/G3 与 Agent 权限分离 | 身份提供者、认证具体方式 |
| 初审→G2 验收→G3 方向裁决→集成→发布分层 | 总工人数、联合方向裁决通过条件与实现方式 |
| 总工只看方向简报；detail pack 有 purpose/TTL | 简报生成方式、脱敏实现 |
| G2 验收、G3 裁决、集成、发布、目标观察分开 | Git/CI/制品/部署平台供应商 |
| 异构能力如实登记，可降级 | 首批支持哪个 CLI、托管适配器实现 |
| 短期有限权限、受限运行与可信证据 | 沙箱/容器/虚拟机及数据驻留方案 |
| 小范围先证明协作有效 | UI 框架、部署成本、HA/RTO/RPO 数值 |

如果这些实现选择现在就被锁死，很容易在尚未证明协作机制的情况下陷入部署与适配细节。下一步应先完成关键协议与场景的设计验证。
