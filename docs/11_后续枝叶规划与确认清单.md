> 状态：**仅规划，不授权实现。** 本文中的确认框只有项目发起人可以勾选；未确认的枝叶不得进入开发。
> 当前工作区基线：T0–T12 已提交；T13（Artifact、OpenAPI 校验、同源文档与 Mock）已实现并通过验证，等待统一审查与提交。

## 1. 生长纪律

每根枝叶都按同一顺序生长：

```text
问题与目标
  → 对象/状态/边界设计
  → 人确认
  → Store / API / CLI 或 Web 实现
  → 单元测试 + e2e + 本项目自用
  → README / AGENTS / 实施计划同步
  → 一层一提交
```

硬规则：

1. **一次只批准一根主枝。** 规划可以同时存在，实现不可并行扩散。
2. **先事实对象，再人工流程，再 AI。** AI 不能早于可版本化、可人工操作的事实对象。
3. **AI 只产出草稿或建议。** 激活约定、发布契约、创建正式任务、评审通过都必须由人确认或明确自动规则执行。
4. **同一事实只有一个来源。** API 文档与 Mock 从 API Contract 生成，不各维护一份。
5. **必须先在 SuperAgentPlusCloud 自身试跑。** 示例不是假数据，而是用系统维护系统。
6. **触发条件未出现，不提前建设。** 多数据库、身份系统、队列与微服务都遵循此条。

### 第二步｜契约驱动协作工作区（推荐下一枝）

**为什么先做人工工作区，再做 AI：** 如果人无法手工维护、查看、校验和发布约定/契约，AI 也无法证明其建议是否可用。先把人工路径跑通，才能知道 AI 应当替代哪一段重复劳动。

#### 页面与能力

项目内新增一级导航 **「契约与制品」**，包含五个标签：

1. **约定包**
   - 团队模板与项目快照；
   - must / should / preference 分组；
   - 版本历史、激活、退役、从模板导入；
   - 每条规则必须有理由与示例。

2. **编排模板**
   - Element Plus 树/表显示 DAG；
   - 节点目的、完成条件、角色提示、依赖和预期产物；
   - 内置 `contract-first-api` 可一键导入项目快照；
   - 不做图形拖拽编辑器。

3. **API 契约**
   - 左侧 operation 列表，右侧契约详情与校验；
   - 结构化显示 path / method / operationId / request / response；
   - 原始 JSON 用成熟编辑器（建议 Monaco Editor），不手写代码编辑器；
   - 草稿保存、校验、发布、历史版本与替代关系；
   - must 违规时发布按钮禁用并显示具体规则。

4. **文档与 Mock**
   - 文档由契约即时渲染；
   - Mock 列出 operationId、method/path、示例响应和可复制 URL；
   - 提供请求测试区，但只请求 Center Mock，不请求真实生产接口。

5. **引用关系**
   - 哪些任务、提交、变更依赖当前契约版本；
   - 契约变更时创建影响候选，但仍由人确认。

#### 页面交付标准

- 人能在浏览器创建约定包、激活项目快照；
- 人能创建/修改/校验/发布 API 契约；
- 文档和 Mock 与契约同步，无第二份编辑入口；
- 历史版本可查，旧版本不被覆盖；
- 用本项目 `/sap-cloud/api/*` 契约走一遍完整流程。

**确认点 G-Workspace：**

- [ ] 下一枝先做人工「契约与制品」工作区；
- [ ] 契约编辑采用“结构化预览 + Monaco JSON 编辑器”，不做完整可视化 OpenAPI 编辑器；
- [ ] 编排模板一期只读/表单编辑，不做拖拽画布；
- [ ] 文档不可独立编辑；
- [ ] Mock 继续挂在 `/sap-cloud/api/mock/:projectId/*`。

### 第三步｜专项 AI 助手（工作区验证后）

不要做一个万能 Agent。四个助手职责分开，可以先共用同一个模型配置，后续再按角色选择不同模型。

#### A. 约定整理助手

**输入：** 团队规范文档、现有约定、项目 active 约定、代码/接口样例引用。

**输出（未生效）：**

```text
ConventionPack 草稿
conflicts[]       # 互相冲突的约定
missing[]         # 缺少但本次需求需要的约定
source_refs[]     # 每条规则的来源
uncertainties[]
```

**门禁：** 不得自行激活；没有来源的规则必须标为推断。

#### B. API 契约设计助手

**输入：** 需求原文、当前主干、active 约定、已有契约版本。

**输出（未生效）：** OpenAPI Artifact 草稿、变更摘要、不确定项、确定性校验结果。

**门禁：** must 违规不可发布；信息不足必须追问；不得自行替代旧契约。

#### C. 任务编排助手

**输入：** 已确认需求、active 约定、选定 WorkflowTemplate、已发布 Artifact。

**输出（未生效）：**

```text
workflow_template_id
convention_checks[]
artifact_refs[]
tasks[]            # node_key / depends_on / role_hint / expected_outputs
artifact_drafts[]
uncertainties[]
```

以 `contract-first-api` 为例：

```text
接口契约确认
  ├─ 前端按同一契约实现
  ├─ 后端按同一契约实现
  └─ 联调测试（依赖前端 + 后端）
```

**门禁：** 只生成 DAG 草稿；人采纳后才创建正式任务。前端/后端必须引用同一个已发布 `api_contract` 版本。

#### D. 规范校验与影响助手

**输入：** 契约、提交、主干变更、active 约定。

**输出（未生效）：** must 违规、should 提醒、可能受影响对象与依据。

**门禁：** AI 不直接给 Review 结论；确定性规则先跑，AI 只补语义判断。

**确认点 G-AI：**

- [ ] 四个助手分开，不做万能 Agent；
- [ ] 先只做 API 契约场景，不做通用工作编排；
- [ ] 所有输出先进入建议/草稿，人采纳后生效；
- [ ] must 规则默认不允许 AI 绕过；
- [ ] 是否允许人记录例外理由后采纳 must 违规草稿：____；
- [ ] 四个助手先共用当前 LongCat-2.5，后续再按角色配模型：____。

## 4. 后续枝干（只记录触发条件）

### F｜项目材料与决定提取

**触发：** 需要把会议纪要、设计文档、甲方意见持续导入项目。

内容：材料上传/引用、会议决定提取草稿、来源定位、冲突提示、待确认决定。不先上向量数据库；先保证来源可查和人工确认。

### G｜团队、身份与授权

**触发：** 两个以上团队真实使用，或准备公网部署。

内容：用户、团队、项目成员、角色、API Token、OIDC/LDAP 可选；把当前字符串 `confirmed_by` 升级为主体引用。

### H｜通知、队列与可靠性

**触发：** 出现无人处理、长期认领、评审积压或外部调用结果未知。

内容：通知订阅、Outbox、幂等命令、租约/超时、备份恢复、运行指标。未达到瓶颈不拆微服务。

### I｜PostgreSQL / MySQL

**触发：** SQLite 单写者成为瓶颈，或组织要求使用现有数据库运维体系。

顺序：先抽数据库方言与仓储接口，再支持 PostgreSQL；MySQL 作为第二适配。不做在线双写迁移。

### J｜Git / CI / DSH / OpenCode 适配

**触发：** 核心链和契约工作区在真实项目中稳定运行。

内容：GitHub/GitLab webhook、CI 事实回填、客户端适配器。Client 仍只通过 Center 协议交互，工具差异留在适配层。
