# 08｜面板产品设计与 URL 契约

> 本文固定 Center 面板的产品目标、信息架构、页面功能和 URL 契约。它不是“给 API 套一个表格”的 CRUD 说明。
> 设计依据：项目的核心不是任务流，而是让当前有效主干、变化理由及影响处置可见、可操作。

## 1. 强制 URL 契约

### 页面

所有页面都位于：

```text
http://127.0.0.1:8787/sap-cloud/*
```

应用基址为 `/sap-cloud/`，Vue Router 使用 `createWebHistory('/sap-cloud/')`。

### API

所有后端接口都位于：

```text
http://127.0.0.1:8787/sap-cloud/api/*
```

例如：

```text
/sap-cloud/api/healthz
/sap-cloud/api/projects
/sap-cloud/api/requirements
/sap-cloud/api/ai/health
/sap-cloud/api/setup/status
```

**旧根路径不再作为正式接口。** 为避免误用，统一返回 308 重定向（GET/HEAD）或 JSON 迁移提示（其他方法）；测试和客户端全部切到新路径。

## 2. 产品目标

面板必须优先回答四个问题：

1. **项目现在是什么样？** 当前有效的目标、范围、能力、规则、接口与数据约定。
2. **为什么是这样？** 每个主干条目的理由、来源、确认人、替代历史。
3. **现在正在改什么？** 待判断需求、在途任务、待评审提交、待处置影响。
4. **改变会影响什么？** 约定变更与任务、提交、文档、测试之间的影响清单。

如果首页只显示“有几个任务、几个需求”，它就是看板，不是本项目。

## 3. 页面信息架构

```text
/sap-cloud/setup
/sap-cloud/settings
/sap-cloud/projects
/sap-cloud/project/:id/overview
/sap-cloud/project/:id/trunk
/sap-cloud/project/:id/requirements
/sap-cloud/project/:id/requirements/:requirementId
/sap-cloud/project/:id/tasks
/sap-cloud/project/:id/tasks/:taskId
/sap-cloud/project/:id/changes
/sap-cloud/project/:id/timeline
```

项目内部统一嵌套在 `/project/:id/*` 下，不再使用 query string 传 project，也不再让页面路径与 API 路径争抢。

## 4. 页面设计

### 4.1 项目列表

不是简单卡片墙。每个项目卡片展示：

- 项目名、目的、状态；
- 当前有效主干条目数；
- 待决需求、进行中任务、未关闭变更、待检查影响数；
- 最后活动时间与“需要人处理”的第一件事；
- 主操作“进入项目”，次操作“新建需求”。

无项目时提供示例项目入口：“用 SuperAgentPlusCloud 自身创建演示项目”。

### 4.2 项目总览（默认首页）

采用三栏布局，而不是统计卡 + 四张重复表：

| 左：项目主干 | 中：需要判断 | 右：正在推进 |
|---|---|---|
| 目标 / 范围 / 关键能力 / 关键约定 | 待评估需求、待确认决定、待评审提交、待检查影响 | 进行中任务、最近提交、开放变更 |

顶部只有四个真正有用的指标：有效主干、待人处理、受阻任务、未处置影响。

下方提供“最近发生了什么”的事件时间线。总览应当让一个刚回来的人 30 秒内知道：项目是什么、哪里变了、下一步该找谁。

### 4.3 主干地图

这是产品核心页：

- 左侧 `el-tree` 展示层级；
- 中间条目详情展示 statement、rationale、来源、确认人与有效期；
- 右侧“引用与影响”：依赖它的任务、需求、变更、替代历史；
- 状态筛选（active / proposed / superseded / retired）默认只显示 active；
- 明确区分“提出条目”和“确认生效”；
- 支持从条目发起“变更此约定”，自动带入 old_item_ids；
- 若条目没有理由或来源，显示“主干质量缺口”，不是静默展示。

### 4.4 需求工作台

需求不是表格的一行，要显示它从原话到决定的演进：

```text
原始表达 → AI 评估建议（未生效） → 人工评估 → 决定 → 拆解任务
```

队列按“此刻需要什么”分组：待补信息、待评估、待决定、已接受待拆解、已结束。默认不把全部状态混在一张表里。

详情页：

- 原文与附件引用置顶，不被摘要替代；
- 自报等级与最终等级并排，差异高亮；
- AI 建议必须显示依据的主干条目、未知项和建议动作；
- 人可以修改建议再采纳；
- 决定完成后，任务草稿才可采纳发布；
- 拆解出的每个任务显示服务哪个主干条目与可检验的完成条件。

### 4.5 任务工作台

分为“可认领 / 我在处理 / 待评审 / 返工 / 已完成”，支持快速认领但不鼓励盲抢。

任务详情围绕一个纵向交付链：任务说明 → 认领历史 → 提交版本 → 评审 → 当前结论。每个提交明确 commit、测试、已知缺口；打回理由逐条对应 done_when。

### 4.6 变更影响台

重点不是变更状态，而是影响项是否处置：

- 顶部展示“旧决定 → 新决定”；
- AI 候选影响单独显示且标记未生效；
- 影响项按 `to_check / affected / not_affected` 分组；
- 每项必须有负责人、判断理由、处置方式；
- 还有 `to_check` 时关闭按钮禁用并提示具体数量；
- “空清单”显示为风险提示：必须明确填写影响评估声明才能关闭；
- 多行编辑采用单行保存或显式“保存全部”，禁止本地残留未保存状态。

### 4.7 时间线

按语义过滤而不是原始事件名：决定、执行、交付、评审、主干变化、影响处置。支持按对象、操作者、日期、关键词过滤；点事件跳回对象详情。

### 4.8 设置与初始化

设置页分区：运行、数据库、模型、面板。敏感字段不回显。保存后立即刷新顶栏状态；需重启的字段列出具体项。

## 5. 示例项目

使用 SuperAgentPlusCloud 自己作为演示项目，种子数据至少包含：

- 主干：维护项目当前有效决定；Center/Client 边界；AI 只产出建议；页面/API URL 契约；SQLite 当前默认；
- 需求：将页面/API 迁移到 `/sap-cloud/*`；完善项目面板；未来支持 PostgreSQL；
- 任务：路由迁移、前端信息架构、演示数据；
- 变更：从“CRUD 面板”替换为“主干与影响工作台”，带待检查影响项；
- 一次打回与重新提交，展示完整交付链。

示例项目必须通过正常 API 创建，不在 UI 里写死假数据。

## 6. 交付标准

- 不是“页面存在”，而是能完成核心动作；
- 每页有加载、空、失败、权限/状态不允许四类状态；
- 建议与已确认内容视觉分离；
- 所有写操作成功后刷新权威状态，失败不假装成功；
- 深链刷新可用；
- 桌面宽度 1366–1920 可用，窄屏至少不横向截断关键操作；
- 使用 Element Plus 现成组件，不自造表格、表单、弹窗、步骤条、树、时间线。
