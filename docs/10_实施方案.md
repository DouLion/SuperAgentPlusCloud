## 2. 生长纪律

1. 一次只批准一根主枝；规划可以并存，实现不并行扩散。
2. 先事实对象，再人工流程，再 AI，最后自动化。
3. AI 只产出草稿；激活、发布、创建正式任务必须由人确认。
4. 同一事实只有一个来源（文档与 Mock 从契约生成）。
5. 先用 SuperAgentPlusCloud 自身试跑，不用演示假数据。
6. 触发条件未出现，不提前建设。

每枝的统一验收：设计先写文档 → Store/API/CLI 或 UI → 单元测试 + `npm test` + `npm run e2e` + web build → 本项目自用一次 → 同步 README/AGENTS → 一层一提交。

## 3. 候选主枝

### A. 契约与制品工作区（面板）

**问题**：T12–T14 的能力目前只有 CLI，人无法在界面里维护约定、编辑契约、看校验、点 Mock。

**交付**

- 项目内新增一级导航「契约与制品」，五个标签：约定包 / 编排模板 / API 契约 / 文档与 Mock / 引用关系。
- 契约编辑：结构化预览 + Monaco(JSON) 编辑器，保存草稿、校验、发布、历史版本。
- must 违规时发布禁用，并指向具体规则与位置。
- Mock 列表给出 operationId、method/path、示例响应、可复制 URL，并提供「试一下」按钮（只打 Center Mock）。
- 需求详情页增加「生成契约编排」，展示 T14 建议，逐项采纳。

**验收**：在浏览器里用本项目自身 `/sap-cloud/api/*` 契约完成：建约定 → 建契约 → 校验 → 发布 → 看文档 → 调 Mock → 采纳编排生成 4 个任务。

**不做**：拖拽画布、完整可视化 OpenAPI 编辑器、独立编辑文档。

### B. 契约变更影响分析

**问题**：契约发布新版本后，已按旧版本实现的前后端任务不会被自动提示。

**交付**

- 契约发布新版本时，自动生成影响候选：引用旧版本的提交、任务、变更（先只做「候选」，不自动改状态）。
- 影响项复用现有 `impact_items`，人逐项处置。
- 面板暴露「本次契约变更影响」。

**验收**：改一版契约，能列出受影响任务并逐项标记继续/调整/复验/作废。

### C. 材料接入与决定提取

**问题**：会议记录、设计文档、IM 讨论目前要靠人手工转述成需求。

**交付**

- 材料导入：粘贴文本或上传 md，形成 `source_refs`。
- AI 提取候选：需求草稿、约定草稿、决定草稿，逐条标注来源与不确定项。
- 人确认后才成为正式需求/约定/决定。

**验收**：把一份真实会议纪要导入，能产出可确认的需求与至少一条约定，且全部带来源。

**不做**：自动接入腾讯会议/飞书/钉钉 API（触发条件未到）。

### D. 团队、身份与授权

**问题**：`confirmed_by`、`worker_id` 目前是自由字符串，无法阻止冒名与越权。

**交付**：成员表、项目成员关系、角色（发起/执行/评审/契约管理）、简单 Token 登录；关键动作校验主体与角色；旧字符串逐步映射为主体引用。

**触发条件**：超过一个团队使用，或需要公网部署。

### E. 通知、队列与运行可靠性

**交付**：站内通知 + 待办订阅、Outbox 重试、认领超时释放、命令幂等、备份与恢复检查、基本运行指标。

**触发条件**：出现长时间无人处理、评审积压、并发写冲突。

### F. PostgreSQL / MySQL 适配

**交付**：抽出数据库方言层（占位符、RETURNING、JSON 列、事务），SQLite 保持零依赖；PG 优先，MySQL 次之；提供从 SQLite 导出的迁移脚本。

**触发条件**：SQLite 单写者成为瓶颈，或组织要求纳入既有数据库运维。

### G. 工具适配

**交付**：Git/CI 只读接入（提交引用、构建结果）、DSH/OpenCode 适配器草案。

**触发条件**：核心链与契约工作区稳定使用后。

## 4. 推荐顺序

```text
A 契约与制品工作区   ← 建议下一枝
B 契约变更影响分析   ← 紧跟 A，复用影响项
C 材料接入与决定提取
D 团队身份授权
E 通知与可靠性
F 多数据库
G 工具适配
```

理由：A 把已有能力变成人能用的东西，是当前最大的落差；B 直接服务「约定会变」这个核心痛点，且能复用现有影响处置；C 之后才需要 AI 承担更多；D–G 都是触发条件驱动。
