# 协作治理、工作契约与生命周期

> 设计提案 v0.3。本文规定协作语义，不规定具体数据库或工作流产品。  
> v0.3 修正：总工只做方向/结构/里程碑裁决，不逐任务看实现；常规交付由独立验收人完成。总工信息隔离见 [总工信息隔离](07_总工信息隔离.md)。

## 1. 先分开执行、初审、独立验收、方向裁决与结果

| 判断 | 谁/什么给出 | 它能说明什么 | 它不能说明什么 |
|---|---|---|---|
| 执行结束 | 执行节点 | 本次尝试已停止，提交了候选结果 | 候选结果正确或满足需求 |
| 证据齐备 | 控制内核 | 必需材料存在，身份、版本、哈希可检查 | 材料本身一定可信 |
| 操作者初审通过（G1） | CLI 背后的真实人 | 此人监督过该候选，认为可以正式提交 | 项目已最终接受、已合并或已上线 |
| 独立验收通过（G2） | 授权独立验收人/领域验收人 | 指定候选满足任务契约，任务可 ACCEPTED | 已安全集成到所有组合版本、已上线或目标已实现 |
| 总工方向/结构裁决（G3） | 授权总工（单人）或总工组（联合） | 方向、结构、里程碑、风险例外可继续 | 对某个 bug 的实现细节负责 |
| 集成/发布成立 | 集成门禁与发布责任人 | 组合版本通过校验；某版本发布到某环境 | 使用后一定达到原目标 |
| 目标结果成立 | 目标责任人与结果证据 | 在约定观察窗口达到了目标，或有明确否定结论 | 之后永远不出现回归 |

正式任务不能由执行者直接设置为 ACCEPTED，也不能把“模型说做完了”映射成 INTEGRATED。没有 CLI 操作者的初审确认，Agent 不能以自己的名义提交；没有 G2 独立验收，任务不能 ACCEPTED；没有 G3，R2/R3 不能实施、里程碑不能接受。**总工不逐任务看 diff/日志；G3 的输入是方向简报，不是实现现场。**

## 2. 身份、角色与权责

### 2.1 四种不能混同的身份

- **Human**：组织/项目里的真实成员。拥有可验证的人类登录身份。
- **Agent**：被授予有限能力的自动化参与者。可提交草案、认领授权任务、报告证据，不具有操作者初审、G2 验收或 G3 方向裁决资格。
- **Runtime**：实际执行的一次 CLI 会话、进程或远端运行实例。它会断线、崩溃、升级、迁移。
- **Accountable human**：这次代理行为对应的人类执行责任主体。不是把 Agent 名称写成负责人；转交责任需要明确记录与接受。

同一个人可以操控多个 Agent；同一个 Agent 模板可在多个 Runtime 中运行。所有正式执行链需能关联到授权人和责任主体，但不由此自动认定法律责任或事故全部责任。

### 2.2 角色按作用域授予，不是固定职级

| 角色 | 核心权力/义务 | 必须限制的动作 |
|---|---|---|
| 发起人 | 提出意图、补充原始背景 | 不能仅因发起就改变公共架构或免除验收 |
| 目标责任人 | 确认问题、优先级、结果指标和取消条件 | 不能静默改动执行中的验收标准 |
| 执行责任人（CLI 操作者） | 认领任务，监督自己名下的 AI 执行；对候选成果做初审确认，认为可交付后以人的身份正式提交 | 不能只让 Agent 自行提交；不能伪造自己的初审；不能同时冒充该任务的独立验收人 |
| 独立验收人（G2） | 对完整候选/证据做任务级验收，决定 ACCEPTED / REWORK；必须不同于执行责任人 | 不能只看 AI 摘要；不能把“总工方向同意”当作任务验收通过 |
| 总工 / 方向裁决人（G3） | 管目标、范围、结构/契约、优先级、风险例外、里程碑；只看方向简报，不读 bug 日志/diff；可单人或联合 | 不能逐任务看实现细节；不能替 G2 验收；不能把“我看过了”当成证据通过 |
| 实现者/协作者 | 在授权范围内产出、测试、反馈阻塞 | 不能擅自扩大范围、使用生产权限 |
| 领域/模块批准人 | 审议影响本领域的结构决策与契约 | 不能越过授权范围批准其他领域 |
| 集成责任人 | 组合多个已验收成果，管理冲突、回归和集成版本 | 子任务都通过时也不能跳过组合验证 |
| 发布责任人 | 确认环境、窗口、风险、回滚与发布对象 | 不得把任务验收等同发布授权 |
| 争议处理人 | 复核初审/验收/方向裁决争议与职责冲突 | 与争议当事人有冲突时应回避 |

成员可以按任务换角色。**任一接入的 CLI 会话都可以向服务器发起意图或认领任务，不需要先具备“经理”身份；服务器把发起关联到背后的操作者，由其承担初审与责任。**总工不是独立的管理层或机器节点：总工本人也是人类终端上的参与者，可以发起、认领、执行和初审自己的成果；但其在本任务上的执行不自动获得 G2 或 G3 的签字权。服务账号也有作用域，不能持有人类初审、独立验收或方向裁决凭据。

### 2.3 三个门：操作者初审、独立验收、总工方向裁决

**G1 操作者初审。** 执行者（通常是操作者名下的 Agent/CLI）产出候选后，操作者必须亲自看过成果与证据，确认“这是我愿意提交的交付”，再以人的身份签署初审并正式提交。Agent 只能提交候选草案与证据声明，不能代替这一步。初审不是开工审批，也不是任务验收。

**G2 独立验收。** 正式提交后，由**不同于执行责任人**的授权验收人（领域验收人/独立验收人）在完整候选与证据上做任务级验收：ACCEPTED 或 REWORK。G2 看的是实现与证据，不是方向；总工不参与这一层的逐任务判断。

**G3 总工方向/结构裁决。** 总工只处理方向层：R2/R3 结构决策、里程碑接受、方向争议、风险例外。输入是**方向简报**（一页：问题、选项、影响、成本、风险、证据指针、建议），不是 diff/日志/复现。总工可以单人，也可以按章程联合；联合裁决绑定同一简报版本与同一组选项。

分层规则：

- **R1 常规任务**：G1 + G2；不需要 G3。
- **R2 结构变更**：实施前需要 G3（结构决策）；实施后仍需 G1 + G2；里程碑再 G3。
- **R3 高风险**：G3 + 人类复核 + G1/G2；不可逆动作单独授权。
- **总工每单签字（可选）**：设 `chief_signoff: per_delivery_brief`；总工只看**交付简报**（能力级变化、风险、证据指针），不看 diff/日志；G1/G2 仍独立完成。
- **总工自己执行的任务**：仍走 G1；G2 由另一名验收人做；若该任务需要 G3，按章程回避或转其他总工。

联合方向裁决的最小规则：

- 所有意见绑定同一 `brief_id`、同一方向包版本、同一组选项；不能把不同简报的通过票拼成一次通过。
- 章程写清：授权名单、通过条件（全体/法定人数/必需职责同意）、异议、僵局。
- 缺席、沉默、超时不等于同意；不允许临时缩减名单凑通过。
- 简报或方向包变化后，旧意见不自动沿用；需要重新发简报、重新裁决。
- 同一人兼任多种职责只计一次有效人类签署。

**独立性与例外（建议，待确认）：** 建议 R2/R3 由不同于执行责任人的总工做 G3；如允许同一人自审，显式标记 `self_direction_review` 并限定风险范围。单人低风险模式可保留，但不能宣传为独立双人审查。结构级变更仍须多人协同批准，不得用“总工单人”绕过。

“每次正式交付有人审批”不意味着每个 Agent 内部推理、工具调用、草稿都单独签字。内部步骤不算独立正式交付。多个低风险成果可在同一验收会话批量处理，但每个 G1/G2 仍绑定具体任务、契约版本、候选对象和证据集合；G3 只按简报绑定方向/结构决策。

## 3. 分级：清晰度与风险两条轴

原案 L1/L2/L3 把执行细节、结构变更、笼统目标混在一个序列中。建议用下述双轴，不把它当作已最终确定的命名。

### 3.1 清晰度 C

| 等级 | 特征 | 下一步 |
|---|---|---|
| C0：可执行 | 目标、范围、验收与约束明确 | 检查风险、权限、依赖后建立正式任务 |
| C1：待澄清 | 问题明确，但有重要缺口或矛盾 | 向目标责任人提少量关键问题，必要时发诊断任务 |
| C2：探索性 | “提速”“变好”“系统不稳定”等目标尚未被定义 | 先定义观察指标和问题范围；只允许受限诊断，不直接改项目 |

### 3.2 变更风险 R

| 等级 | 典型工作 | 开工规则 | 交付/发布规则 |
|---|---|---|---|
| R0：受限探索 | 只读分析、文档草稿、沙箱基准测量 | 在项目已授权的数据、范围和预算内直接推进 | 需要适合该类成果的证据、操作者初审 + G2 验收 |
| R1：边界内变更 | 已有接口内的 bug 修复、小范围实现、测试补充 | C0 且符合既定政策即可直接认领，无逐单开工审批 | 必须验证、操作者初审 + G2 验收；G3 默认不介入；集成、发布仍有门禁 |
| R2：结构/契约变更 | 公共接口、模块边界、核心依赖、数据模型、架构决策 | 多人协同讨论与批准生效后，才释放实施契约 | 受影响领域复核、组合验证与相应发布授权 |
| R3：高后果动作 | 权限/密钥、生产数据、不可逆迁移、外部费用和高影响发布 | 专门风险审议；身份、演练、备份/补偿等前置条件 | 独立复核、明确人类授权、有限窗口与事后验证 |

R2 不意味着一定要新建一个大服务，例如只改一个公共 API 字段也可能是结构变更。R1 也不由代码行数决定。R0 读取敏感数据仍可能升级到 R3；“只读”并不意味着无隐私风险。

### 3.3 谁决定等级

1. 提交者声明预期等级与影响。
2. AI 提出分类建议、依据与不确定性；不作为最终授权事实。
3. 内核用确定性政策检查保护路径、接口、数据/环境权限和已有契约。
4. 出现不确定性、政策冲突或变更超范围时，先 HOLD 受影响动作，由有权的人裁定。
5. 降低等级需要依据与有权裁定；不能靠模型反复改写需求绕过。

所有检查应在建单、认领、初审、提交、G2 验收、G3 方向裁决、集成和发布等关键边界再次执行。执行中发现结构性问题，必须提出新提案，而不是把架构变更藏进一个 R1 修复。

## 4. 从原始意图到工作契约

### 4.1 意图不是任务

原始意图保留原文、提出者、来源权限、时间和目标关联；AI 摘要与推测单独存放。去重可以链接同一问题，但不能因为模型认为相似就丢弃不同提出者的事实。

进入 READY 前，正式任务至少回答：

| 工作契约字段 | 必须回答的问题 |
|---|---|
| 问题与目的 | 解决什么问题，为什么现在值得做？ |
| 范围与非目标 | 可以改变什么？明确不做什么？ |
| 结果/交付物 | 代码、接口、文档、分析结论还是其他成果？ |
| 验收条目 | 每项怎样被人或机器判断，在哪个场景下？ |
| 证据要求 | 哪些材料由执行者提供，哪些需要可信环境复核？ |
| 基线与依赖 | 基于哪个仓库版本、决策版本、接口约定？ |
| 权限与风险 | 允许哪些工具、数据、环境和外部副作用？ |
| 责任与审批 | 谁监督代理、谁做操作者初审、谁做 G2 独立验收、谁做 G3 方向裁决、是否 `per_delivery_brief`、谁处理集成？ |
| 资源与停止条件 | 时间/费用/并发预算多少，何时该停止或求助？ |
| 契约版本 | 谁确认过，是否属于已批准提案的实施范围？ |

测试证据是代码任务的一部分；研究任务可以交付实验设计、原始测量、分析局限；文档任务可以交付内容来源、检查清单和评审意见。不能要求所有任务都“有单元测试”，但**必须有与验收条目相匹配的证据**。

### 4.2 版本变化规则

- 正式契约每一版本不可被原地改写；当前版本指针可以推进。
- 未开工任务可重新生成契约，并重新检查风险/依赖。
- 已开工后，范围、验收、关键基线或有效决策变化产生新版本；记录原因、批准人、影响和迁移方式。
- 旧版本成果仍可保留为候选，但不得自动按新版本通过。内核要求重新比对，必要时补做或停止。
- 初审操作者、G2 验收人或 G3 总工发现需求本身遗漏，应提出 `RequirementChange`，不能用 `ImplementationDefect` 掩盖。
- 语义性变更不能仅因文字差异小而被免除复核；轻微错字修订也需留版本关联，但可由政策认定不影响执行条件。

## 5. 多人协作：目标组、任务与尝试

建议采用三层，而非“一个任务谁抢到就是谁的”：

1. **协作组（Work Package）**：围绕一个可整体验收的结果，记录子任务、依赖与集成责任人。
2. **正式任务（Task）**：一个明确边界和契约版本，默认只有一个当前执行责任主体。
3. **执行尝试（Attempt）**：同一任务的一次运行；重试、换工具、换执行者都生成新记录。

多人同时实现的两种方式：

- 不同子任务：各自认领，有明确接口与依赖；在组级做组合验收。
- 同一任务结对：一个责任人持有主租约，其他人为被授权协作者；各自工作副本或明确单写者，不共享不受控写入权限。

会议文档可以多人协同编辑，但文档草案不等于有效决策。代码的多工作副本也不代表可以同时无序地写同一共享数据库、生产服务或外部资源。

### 5.1 调度不只有“派单”

支持主动认领、邀请认领、指定责任人与系统推荐。推荐依据能力、权限、数据驻留、可用容量、费用和协作依赖，不把某个模型“最强”当作通用策略。**发起同样不绑定特定入口：任一接入的 CLI 会话都可以把意图送到服务器，服务器再将其关联到背后的操作者。**

READY 只是满足发布到任务池的条件。依赖、有效契约、执行容量与初审/G2/G3 容量未满足时，标记 HOLD，不释放执行权。明确记录任务无人认领、等待领域决策、等待初审、等待验收、等待方向裁决、等待集成等瓶颈。

任务依赖支持至少以下语义：

- **硬依赖**：前序指定产物/接口版本未就绪，后序不得启动。
- **软依赖**：允许用明确假设、mock 或 stub 探索，但不能作为集成完成依据。
- **冲突约束**：共享资源、公共接口或迁移要求串行/协调，不是简单 DAG 前后关系。

硬依赖图应无环；发现环说明拆分或契约有问题，应回到规划。整个项目记忆图可以有反馈关系，不应强迫所有关系都是 DAG。

## 6. 状态模型

### 6.1 Task：正式工作的交付生命周期

| 状态 | 含义 | 下一步与条件 |
|---|---|---|
| DRAFT | 契约未满足准入要求 | 完善后发布为 READY；或 CANCELLED |
| READY | 准入成立，尚无人持有效执行权 | 原子认领、授权、容量与依赖通过后 ACTIVE |
| ACTIVE | 持有效租约执行 | 操作者初审确认并合规提交、证据准入通过时，关闭该尝试执行权并进入 IN_REVIEW |
| IN_REVIEW | 不可变候选等待 G2 独立验收；无持续执行写权 | 独立验收通过 → ACCEPTED；要求修改 → REWORK |
| REWORK | 验收要求修改 | 前一执行权已关闭、无 HOLD 且其他准入成立后，原子重认领创建新 attempt/lease/token → ACTIVE；再整改补证、重新初审提交 |
| ACCEPTED | 独立验收人接受指定候选成果 | 代码经组合验证与集成记录后 INTEGRATED；非代码成果按契约发布/归档后 INTEGRATED |
| INTEGRATED | 成果纳入指定项目基线或成果集合 | 任务交付链完成；不自动代表上线或目标达成 |
| CANCELLED | 正式停止此项工作 | 保留原因、已有证据与后续替代任务；不得伪装为通过 |

`PRIMARY_CONFIRMED`（操作者初审确认）是提交前的**事件/签署**，不是独立 Task 状态：它随正式提交一起被内核记录，缺少它就不能进入 IN_REVIEW。`IN_REVIEW` 表示候选已离开操作者，正在等待 G2 独立验收；G3 方向/结构裁决不在 Task 状态里，它是 Decision/Milestone 的对象。

`HOLD` 是附加约束，不是一个吞掉原状态的通用列。例如 `ACTIVE + HOLD(decision_invalidated)` 或 `IN_REVIEW + HOLD(evidence_expired)`；保留原阶段与所有阻塞原因。每个阻塞都有来源、解除条件、处理人和升级时间。

- HOLD 时不能启动新尝试、正式提交、裁决通过、集成或发布受影响成果。
- 可以报告状态、存储隔离候选、解释问题、取消或在独立授权的诊断契约内调查。
- 租约失效不自动表示人放弃或任务失败：保留 ACTIVE 阶段，加 `lease_lost`；确认没有有效执行权且完成副作用核对后可回 READY。
- 需求撤回、重复任务、决策改变和无法完成应有不同取消原因，不都算执行质量差。
- 已集成任务若发现缺陷，建立关联缺陷/回滚任务与事故记录；不删除原验收事实。

### 6.2 Attempt、Review、Decision、Release 分开记录

| 对象 | 建议状态 | 关键意义 |
|---|---|---|
| Attempt | CREATED / RUNNING / FINISHED / FAILED / EXPIRED / CANCELLED | FINISHED 只是一次运行结束；不推进为 ACCEPTED |
| Primary attestation | PENDING / CONFIRMED / WITHDRAWN | CLI 操作者对该候选的初审签署；缺失则不能正式提交 |
| Acceptance (G2) | WAITING / IN_PROGRESS / APPROVED / CHANGES_REQUESTED / VOID | 每轮绑定不可变候选；独立验收人签发任务级结论 |
| Direction brief | DRAFT / ISSUED / SUPERSEDED | 信息闸门生成的一页方向简报；总工只读这个 |
| Direction decision (G3) | PROPOSED / ACTIVE / REJECTED / DEFERRED / SUPERSEDED | 绑定 brief/方向包版本；不逐任务判实现 |
| Review appeal | OPEN / RESOLVED / DECLINED | 独立争议对象，不把有争议成果直接放行 |
| Decision | PROPOSED / ACTIVE / CONTESTED / SUPERSEDED / WITHDRAWN | 有效决策需要有权人确认；挑战不是静默替换 |
| Release | PLANNED / AUTHORIZED / DEPLOYING / RELEASED / FAILED / ROLLED_BACK | 绑定组合版本、环境和发布授权，不与任务状态混用 |
| Outcome observation | PLANNED / OBSERVING / MET / NOT_MET / INCONCLUSIVE | 记录目标结果，而不是输出量 |

正式提交在权威事务中同时固定候选、记录操作者初审签署、关闭该尝试执行权并建立 G2 验收请求。后续验收不要求已经关闭的执行租约继续有效，只要求候选来源、当前契约/决策、证据与验收授权有效。验收驳回不覆盖 Attempt 的结束事实；任务重试不删除历史。REWORK 必须先合法取得新执行权，之后才整改补证、重新初审提交。通过后候选对象或契约发生变化，需要重新初审与 G2 验收；若该变化影响方向/结构，另发 G3 简报。

### 6.3 必须成立的不变量

1. 一个任务同一执行槽只有一个当前有效租约；协作/试验副本不能争夺同一正式写权。
2. 没有有效契约、权限与人类责任主体，不能进入正式 ACTIVE。
3. Agent 凭据不能发出操作者初审、G2 独立验收或 G3 方向裁决，也不能发出结构批准裁决。
4. 正式提交必须绑定操作者初审签署；没有真实人类初审的候选不能进入 IN_REVIEW。
5. ACCEPTED 必须来自有效 G2：由不同于执行责任人的授权验收人签发，绑定同一候选版本。
6. G2 验收必须指向精确的契约版本、候选哈希、证据清单快照与验收规则版本。
7. G3 方向裁决必须绑定同一 `brief_id`、方向包版本与选项；总工不读操作层原文，不能以“看过日志”为由放行。
8. ACCEPTED 不推出 INTEGRATED；INTEGRATED 不推出 RELEASED；RELEASED 不推出 MET。
9. 决策/契约失效或候选变化时，相关初审、G2、G3 与门禁不得继续使用旧上下文。
10. 正式状态由内核处理命令后推进，不由客户端上传整个状态覆盖。
11. 重复反馈不能生成重复认领、初审、验收、方向裁决、交付计数或发布副作用。
12. 修改需求、验收错误、环境故障与实现缺陷可区分；责任与指标不以一次驳回自动归罪。
13. 原始初审、G2、G3、纠正与撤销记录可共同追溯；不能靠删除历史制造“始终成功”。

## 7. 协同决策：有结论的会议，不是聊天即共识

### 7.1 触发条件

结构/契约变更、跨领域取舍、重大需求矛盾或高后果动作需要协同讨论。笼统问题先补证据与定义，再决定是否需要会议；不是所有 C2 都直接召集所有人。

低风险澄清可异步完成。R2 必须有多人共同讨论并明确确认，形式可以是有来回讨论的异步文档/画板，也可以是同步会议；只有静默“已读”不算参与，更不算同意。

### 7.2 会议/讨论输入

- 要决定的具体问题与目标，而不是“大家聊一聊”。
- 当前有效决策、受影响领域和相关证据。
- 至少可比较的选项，包含“不做/先测量”选项。
- 成本、风险、回滚/迁移方案和不确定性。
- 有权参与者、必需职责、时间盒和僵局处理方式。

AI 可以主持、检索、生成图示、提出反例和整理意见，不能冒充人的投票。来自会议附件的指令仍是待讨论内容，不自动获得执行权限。

### 7.3 有效结论最小集合

问题、选择、未选方案与原因、适用范围、假设、需要复核的条件、批准人、未决异议、实施契约、验证与回滚方案、决策版本。

- 不要求全员一致，也不允许简单多数覆盖有明确安全职责的人。
- R2 默认至少两名不同的授权人，覆盖目标与相关模块职责；受影响必需领域必须明确同意。有权拒绝的职责、审批法定人数与委派方式在项目章程里写清。
- **G3 结构决策的输入是方向简报（一页），不是代码 diff/日志**；需要细节时走 scoped detail pack，不把操作现场灌进总工上下文。
- 超时不能默认为通过。僵局交由预先指定裁决人处理；无法裁定则继续 HOLD，或批准受限实验，不把争议拆成多个低风险任务偷渡。
- 会议纪要与 AI 摘要是草案。授权人确认具体 Decision 版本后，内核才激活并释放对应契约。

### 7.4 决策失效传播

挑战旧决策 → 记录依据与影响猜测 → 查找显式依赖并补充语义影响分析 → 对受影响任务/初审/G2/G3/集成候选加 HOLD → 通知责任人 → 多人审议替代或维持 → 新版本生效 → 逐项确认上下文刷新、补证或取消 → 解除相应 HOLD。

不是所有挑战都要停掉整个项目，也不能承诺依赖图覆盖所有真实影响。对疑似影响按风险保守处理；未受影响任务可继续；安全诊断可以另行授权。旧执行节点即使漏收通知，也会在后续门禁因版本失效被拦截。

## 8. 初审、独立验收、方向裁决与驳回

### 8.1 操作者初审（G1）

操作者在正式提交前至少确认：

- 这是自己监督的那份精确候选，而不是另一个会话或旧版本。
- 契约条目与证据逐项对应，未验证项被如实标出。
- 没有已知的高风险副作用、越界改动或伪造证据。
- 愿意以人的身份对该候选的提交负责。

初审可以退回给自己的 Agent 继续修改，不产生 G2 验收轮次，也不计入验收返工。初审签署后，候选固定；若候选再变化，必须重新初审。

### 8.2 独立验收包（G2）

独立验收人应拿到：问题/非目标、契约条目、具体候选 diff 或成果、逐条证据、独立验证结果、操作者初审签署与说明、旧轮驳回的响应、未验证部分、风险与回滚/撤销方法。不能只给一个“通过”按钮和一段 AI 自我总结。

业务可用性需要人的场景判断；不确定的内容应显示“未验证”，而不是让 AI 生成一个可信度分数掩盖缺口。

**G2 的输入是完整实现现场；这不是总工的输入。** 总工不读这份包，除非发起 G3 且走按需细节包。

### 8.3 独立验收裁决（G2）

G2 验收人记录：逐条判断、未验证风险、裁决（APPROVED / CHANGES_REQUESTED）、绑定的候选与契约。APPROVED 表示任务 ACCEPTED，不表示集成、上线或目标达成。

- 单人验收：授权验收人通过即可。
- 高风险/多领域可设多名验收人，按章程汇总；缺席不等于同意。
- 验收人必须不同于执行责任人；总工的方向同意不能替代 G2。

### 8.4 方向简报与总工裁决（G3）

G3 只处理方向/结构/里程碑。信息闸门把请求压成一页简报，总工只看简报与方向包，不读日志/diff/复现。

简报最小字段：决策问题、方向关联、选项（含不做/延后）、影响、成本、可逆性、风险、已知未知、证据指针、提交者建议、截止时间。

规则：

- **简报不含** stack trace、逐行 diff、调试对话、原始日志；出现则退回闸门。
- 总工可以要求 `detail pack`（purpose + TTL），在独立会话查看；看完只写结论 + 证据指针，不把原文回填主上下文。
- 单人 G3：授权总工通过即可；R2/R3 按章程可要求多名总工联合。
- 联合 G3：绑定同一 `brief_id`、方向包版本与选项；缺席/超时不等于同意；不能拼不同简报的票。
- 总工每单签字（可选）：`per_delivery_brief` 时只看交付简报（能力级变化、风险、证据指针），不看实现现场；G1/G2 仍独立完成。
- 简报或方向包变化后，旧 G3 意见不自动沿用。

### 8.5 驳回必须可响应

| 分类 | 例子 | 正确处理 |
|---|---|---|
| ImplementationDefect | 违反 A2 接口约定，给出失败复现 | REWORK，修实现并补证 |
| EvidenceGap | 缺少规定环境的验证 | 补证；不必默认重做代码 |
| RequirementChange | 新发现业务必须支持原未约定场景 | 新契约/新任务，明确范围与时间影响 |
| AcceptanceError | 验收人看错证据/条目 | 复核与纠正原裁决，保留关联 |
| EnvironmentFailure | CI 故障、测试环境不可用 | HOLD/重测，不记成实现缺陷 |
| IntegrationConflict | 单项可行但组合不兼容 | 集成责任人协调补充任务或契约变化 |

每条理由包含验收条目、事实/复现、期望与实际、最小整改或所缺证据。无法机器验证的体验问题仍可以驳回，但要说明真实场景和契约依据，而不是假装所有理由都是客观技术断言。

### 8.6 申诉与反复返工

操作者可就标准漂移、证据误读或职责冲突提出申诉；G2 验收人或总工也可就操作者隐瞒风险、证据不足或方向偏离提出升级。申诉期间受影响成果不放行，不暂停无关工作。由未涉冲突的授权人复核；裁定结果可以纠正驳回、确认变更或维持结论。

连续返工超过项目阈值时，系统应触发“契约/上下文/验证方式复诊”，不是无限重试或自动降低个人信誉。预算告警与停止条件先于绩效判断。

## 9. 注意力也是有限资源

- 开工并发应受**初审、G2 验收与 G3 方向容量**约束，而不只看空闲 Worker。
- 只有需要人决策、可初审/验收成果、方向/结构升级、阻塞/风险升级、预算越界等关键事件需要及时通知；普通进度按摘要推送。
- 每个阻塞明确“等谁、等什么、多久升级”；看门狗判断没有可观察进展只能提出诊断，不直接判定人无贡献。
- 人类签字必须可理解；减少初审与 G2 的阅读成本比增添模型更值得先验证；G3 只读简报，不读实现现场。

## 10. 追溯与绩效的边界

本系统先记录工程事实，再允许经过治理的分析扩展。默认不建设人员排名，不自动推断 AI/人类价值比例，不把负面诊断或主动叫停视为低产出。

原案 A/B 示例需要纠正：100 个通过任务、200 或 300 次提交，只能得到 **提交通过占比 50% / 33.3%**。若每个任务分别均被驳回一次或两次，两人的**任务首次通过率都是 0%**。若只知道提交总量，则无法推断任务首次通过率。

建议区分：

- 任务首次通过率 = 首次正式提交即获 G2 验收通过的任务数 / 有过首次 G2 验收的任务数。操作者初审退回不计入该分母。
- 平均返工轮数 = G2 验收缺陷导致的额外正式提交轮数 / 同范围统计的已验收任务数。
- 初审退回、G2 驳回、方向裁决等待、需求变动、环境失败和集成返工分别统计。
- 取消、探索、负面结论、任务难度与协作者贡献单独标记，不伪装为可简单比较的分数。

A 在相同难度、相同标准、相同缺陷原因与相同审核条件下可能更有效率；仅凭总数不能得出“A 绩效一定更高”。结构化数据降低取证成本，但没有消除评价中的判断与权力。

如果后续启用贡献分析，应具备目的限制、成员可见、数据最小化、解释、纠正与申诉；不允许某个可选绩效模块反向修改核心验收标准或跳过人类授权。
