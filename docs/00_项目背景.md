# 00｜项目背景与问题定义

> 本文说明项目为什么需要做，以及它要解决和不解决什么。核心概念见[02｜核心概念与原则](02_核心概念与原则.md)，系统结构见[03｜总体架构](03_总体架构.md)。

## 1. 背景：项目会持续变化

定制化软件通常从多轮会议和初步设计开始。需求、数据结构、接口和模块边界逐步明确；开发开始后，难点会暴露，接口和数据库设计可能需要调整。甲方阶段性检查、验收意见和实际用户反馈，又会带来新要求。早期方案因此可能部分失效，项目仍需继续演进。

这类变化本身并不异常。真正的问题是变化发生后，项目成员常常无法共同回答：

- 现在有效的决定是什么？
- 为什么这样决定，谁确认的？
- 旧决定何时、因为什么被替换？
- 哪些在做的任务、已提交的实现或文档受到了影响？

若这些答案散落在文档、聊天、代码和个人记忆中，项目便会逐渐变得难以维护，甚至全程参与者也难以准确还原来龙去脉。

## 2. AI 协作让问题更明显

AI 辅助开发降低了跨语言和实现细节的门槛，但没有自动解决项目背景共享问题：

1. 单次会话上下文有限，长时间调试和临时工作容易挤掉早期约定。
2. 会话中断时，未完成事项、已验证结论和临时假设容易混在一起。
3. 跨会话或跨人员协作时，方向性和细节性约定都可能丢失。
4. AI 可能在信息不足时自行补全前提或作出决定；如果没有明确标记，就会被误当成项目结论。
5. 多人并行开发时，每个人或 Agent 对项目当前状态的理解可能不同。

核心问题不是“让 AI 拥有无限上下文”，而是让不同的人和会话能够从同一份可靠记录中恢复必要背景。

## 3. 共同问题

这些经历可以归纳为三类：

### 3.1 决策没有成为可追溯的事实

方案、接口、数据结构或业务规则发生变化，但“谁在何时基于什么理由确认了什么”没有留下清楚记录。后来发生争议时，只能依赖记忆和零散聊天。

### 3.2 当前有效状态没有唯一来源

设计文档、代码、会议纪要和个人记忆可能分别包含不同版本。成员难以判断哪个来源代表当前有效决定。

### 3.3 背景无法可靠继承

换人、换会话或隔一段时间继续工作时，项目要重新解释背景；重新解释过程中也容易遗漏或改写原意。

## 4. 现有工具各自有用，但不能单独解决问题

| 工具或做法 | 擅长的事 | 单独使用时的缺口 |
|---|---|---|
| Git | 记录代码版本与差异 | 通常不完整记录业务决定及其理由，也不自动说明决定何时失效 |
| 设计文档 | 表达阶段性方案 | 可能滞后于实际演进，且多份文档可能冲突 |
| 任务看板 | 跟踪执行状态 | 通常不维护项目当前有效的关键约定 |
| 审批流 | 约束批准程序 | 流程合规不等于项目决定正确，也不一定能说明影响范围 |
| 聊天与会议记录 | 保留交流过程 | 难以稳定区分提议、讨论、决定和已失效信息 |
| AI 会话 | 帮助分析和实现 | 上下文有限；模型输出不自动成为经过确认的项目决定 |

本项目不取代这些工具，而是为项目关键决策建立一个可查、可继承、可追溯的权威记录，并与原始材料、任务及代码版本建立关联。

## 5. 目标与非目标

### 目标

- 能查到项目当前有效的关键决定与约束。
- 能追溯决定的来源、理由、确认人和历史变化。
- 能让需求、执行任务和代码提交关联到相关决定。
- 重要决定变化时，能登记潜在影响对象并逐项处置。
- 让人和 AI 在不同会话中读取同一份项目背景，减少自行补全和重复解释。

### 非目标

- 不承诺让 AI 自动完成项目或自动作出所有项目决定。
- 不试图消灭需求变化；目标是让变化明确、可追踪。
- 不替代 Git、文档管理、项目管理和会议系统。
- 一期不做人员绩效、贡献排名或复杂审批矩阵。
- 不要求所有实现细节、讨论过程和调试日志进入权威主干记录。

## 6. 成功的基本判断

系统是否有价值，不能只看对象数量或自动化程度。至少要验证：

1. 新成员或新会话能否找到当前有效的关键约定。
2. 重要约定变化后，能否说明哪些任务、提交或文档需要检查。
3. 提交的实现能否对应任务和可检验的完成条件。
4. 记录与确认的成本是否低于减少的返工、误解和追溯成本。

若流程比问题本身更重，或主干记录长期无人维护，系统就没有达成目标。
