# 工作契约、决策、交付与异常模板

> 用于设计评审和纸面协作演练。这里的表单字段不是数据库 DDL、接口实现或真实审批记录。  
> 模板中的“填写”项应由具体项目补全；示例中的对象 ID、人物、commit 名称、指标均为虚构演练数据。

## 1. 项目章程模板

| 项目项 | 填写内容 |
|---|---|
| 项目/目的 | 项目 ID；为谁解决什么问题；不以什么作为成功 |
| 当前目标 | Goal ID、目标责任人、基线、观察指标与窗口 |
| 可发起成员 | 人员/受限系统来源；匿名/外部意图如何审核 |
| 普通工作授权 | R0/R1 允许的范围、资源、数据和工具；无需逐单开工审批的条件 |
| 结构决策规则 | 哪些属于 R2；必需领域职责；至少两名不同批准人；异议与僵局规则 |
| 高后果规则 | R3 的前置条件、独立复核、演练、备份/补偿与发布授权 |
| 初审规则 | CLI 操作者如何确认候选、签署人资格、退回与重新提交规则 |
| G2 验收规则 | 授权验收人名单；是否多人验收；通过条件；必须不同于执行责任人 |
| G3 方向裁决规则 | 授权总工名单；单人/联合；通过条件（全体/法定人数/必需职责）；简报规则；异议、否决、僵局与委派 |
| 自审限制 | G2 不得由执行者兼任；G3 做自己执行成果时是否允许、如何标记、风险上限 |
| 集成与发布 | 组级集成责任人、发布人、目标基线/环境、回滚与操作核对方式 |
| 节点能力 | 已验证/未知的工具动作、隔离、取消、恢复、证据与数据驻留 |
| 容量与停止 | 执行、初审、G2 验收、G3 方向裁决、集成在制品上限；预算；失联与反复返工升级 |
| 数据与审计 | 最小上传范围、访问与保留、密钥隔离、纠错/删除、贡献分析是否启用 |
| 有效版本 | 章程版本、确认人、适用项目范围、生效条件与复核触发 |

章程不能写成“所有人都有所有权限”，也不能写成“所有事情都找某个经理”。必须有作用域，且不隐含赋予 Agent 操作者初审、G2 验收或 G3 方向裁决资格。

## 2. 意图与诊断模板

### 2.1 原始意图

| 字段 | 要求 |
|---|---|
| Intent ID / 来源 | 原始渠道与可访问引用；保留原文 |
| 提出者 / 时间 | 人/系统身份；服务器记录时间；外部时间单列 |
| 问题与受影响者 | 谁遇到什么，举出至少一个观察场景 |
| 目标关联 | 属于哪个 Goal；如果未知，标记未知，不凭空生成业务目标 |
| 清晰度 | C0/C1/C2 及理由；关键缺口/矛盾 |
| 预期风险 | R0/R1/R2/R3、影响范围、判定依据与不确定性 |
| 先问的问题 | 只列改变方向的关键问题；不要把所有技术细节丢给提出者 |
| 下一步 | 可建契约、需澄清、受限诊断、协同决策、重复关联或明确拒绝 |

### 2.2 诊断任务

问题/假设、可访问数据、测量方法、只读/沙箱范围、允许成本、禁止动作、比较选项、结论 G2 验收人与 G3 总工、停止条件。

输出必须允许以下结论：可实施、应改方向、不应实施、证据不足。结论附原始依据和局限；“多写些建议”不是验收标准。

## 3. 协同决策模板

| 字段 | 要求 |
|---|---|
| Decision ID / Version | 独立版本，状态 PROPOSED/ACTIVE/CONTESTED/SUPERSEDED/WITHDRAWN |
| 问题 / Goal | 要决定什么，为什么现在需要决定 |
| 现有依据 | 当前决策、契约、数据与仓库基线；区分事实、假设、争议 |
| 选项 | 至少可比较的备选；保留不做/先实验选项 |
| 选择与未选原因 | 可解释取舍，不用“AI 推荐”代替理由 |
| 适用范围 / 非目标 | 哪些模块、用户、接口与环境；哪些情况不覆盖 |
| 关键假设 | 假设成立的证据、有效条件与复核触发 |
| 风险 / 迁移 / 回滚 | 哪些副作用可撤销，哪些不能，如何验证 |
| 讨论参与者 | 真实身份、覆盖职责、意见、未决异议；不把 AI 代理算做人类投票 |
| 批准要求与确认 | 必需职责/人数；各人确认的精确版本；不能以已读代替批准 |
| 实施输出 | Work Package、Task、Contract 的引用及依赖门槛 |
| 失效影响 | 被替代决策、受影响对象、治理代次与 HOLD/恢复计划 |

批准后的决定仍可能错误；其价值是可检验、可替代、能追踪为何这样做。未决异议应保留，不被“共识摘要”抹去。

## 4. 正式工作契约模板

| 字段 | 要求 |
|---|---|
| Project / Goal / Work Package / Task | 一项正式工作属于什么目的与协作组 |
| Contract Version / Hash | 正式版本与内容摘要；来源 Decision 引用 |
| 问题 / 目的 | 不只写操作，要写解决的真实问题 |
| 范围 / 非目标 | 可修改的对象/契约，不能触及的范围 |
| 交付物 | 代码、文档、分析、接口或组合成果；纳入项目的方式 |
| 验收条目 A1...An | 可观察的期望；机器检查与人类判断分别标注 |
| 证据矩阵 | 每项对应所需证据、可信来源、环境与已知局限 |
| 基线 / 决策 / 依赖 | 精确引用；依赖是接口已批准、证据通过、已验收还是已集成 |
| 风险 / 授权 | 风险依据、批准来源、允许工具/数据/副作用 |
| 责任与审批 | 谁监督代理、谁做 G1 初审、谁做 G2 验收、谁做 G3 方向裁决、是否 `per_delivery_brief`、谁处理集成？ |
| 预算 / 停止 | 成本、时间、并发、自动返工阈值；停下后找谁 |
| 变更处理 | 需求/结构变化如何新建版本，旧尝试与成果如何处理 |

**契约准入检查**：别人能知道为何做、什么不做、按什么验收、遇到什么应停止吗？答案为否则先澄清，不因模型能生成代码就放行。

## 5. 进度、候选与证据模板

### 5.1 观察性进度

Task/Attempt/Runtime、当前契约、已完成可观察步骤、遇到的阻塞、风险/假设变化、剩余计划、预算消耗、需谁判断。

进度不是客户端覆盖状态的权限，也不是强制公开私人思考过程。没有可观察进展时应诊断原因，而不是自动判断人员低贡献。

### 5.2 提交前的操作者初审

操作者在签署初审前，至少确认：

- 候选就是自己监督的精确对象，不是旧会话或另一分支。
- 契约条目与证据逐项对应，未验证项已如实标出。
- 没有已知的越界改动、高风险副作用或伪造证据。
- 愿意以人的身份为该候选的提交负责。

初审签署记录：初审人、候选哈希、契约版本、证据清单快照、签署时间、退回理由（如退回）。

### 5.3 G2 验收包（不是总工简报）

| 字段 | 要求 |
|---|---|
| 身份与来源 | Project、Task、Attempt、Runtime、grant、执行责任人 |
| 提交前执行权 | 当前 lease、authority_epoch、fencing_token；核对未到期/撤销/关闭、无相应 HOLD |
| 工作依据 | Contract version/hash、Decision versions、治理代次、仓库基线 |
| 精确候选 | commit/内容摘要、diff/成果引用、可访问权限 |
| 操作者初审 | 初审人身份、签署时间、候选与证据快照引用；缺失则不得提交 |
| 验收映射 | A1...An 分别给出证据，不能只有“所有测试通过” |
| 可信复核 | 验证策略/测试集版本、环境、独立运行身份、原始结果与摘要 |
| 未验证项 | 未覆盖场景、暂存假设、风险，显式写未知 |
| 整改响应 | 旧轮每条理由对应的新证据/实现变化，或提出标准变更 |
| 集成/撤销 | 兼容性、迁移、组合要求、回滚/撤销边界 |
| G2 规则 | 授权验收人名单；是否多人；通过条件；必须不同于执行者 |

提交成功时固定候选、记录初审签署、关闭该尝试执行权并建立 G2 验收。验证可以异步补充独立材料；每项材料/证据清单版本保持可追溯，G2 裁决必须绑定当时完整且不可变的证据清单快照，不能在通过后悄悄替换材料。

迟到旧尝试只允许隔离导入，不自动恢复正式提交资格。G2 时无需已关闭的执行租约仍有效，但当前候选、契约/决策、证据、初审签署和验收授权仍须有效。

### 5.4 G3 方向简报包（总工只看这个）

| 字段 | 要求 |
|---|---|
| 简报 ID / 版本 | brief_id、方向包版本、生成时间、生成者 |
| 决策问题 | 一句话：需要总工决定什么 |
| 方向关联 | 属于哪个目标/有效决策；不做会怎样 |
| 选项 | 至少两个，含不做/延后/缩小 |
| 影响 | 范围、成本、周期、可逆性、受影响领域 |
| 风险 | 最坏后果、已知未知、触发条件 |
| 证据指针 | 路径/commit/报告链接；**不贴日志正文** |
| 建议 | 提交者建议与理由，标明是建议 |
| 截止 | 何时必须决定；超时默认 HOLD |
| 已过滤 | 明确写“已排除操作细节”；列出被排除类别 |

**G3 包不含**：stack trace、完整 diff、逐行代码、调试对话、原始日志。需要细节时走 scoped detail pack（purpose + TTL），不合并回总工主上下文。

## 6. G1 初审、G2 验收、G3 方向裁决与申诉模板

### 6.1 操作者初审（G1）

Primary Attestation ID、初审人、Task、Contract、候选摘要、证据清单快照、自检结论、未验证项、签署时间、退回时的理由。

初审只有 CONFIRMED 或 RETURNED 两种结果；退回给执行者继续修改，不建立 G2 验收轮，也不计入验收返工。

### 6.2 G2 验收裁决

G2 记录：验收人身份、G2 规则版本、Task/Contract/候选/证据快照、逐条判断（APPROVED / CHANGES_REQUESTED / WAITING / VOID）、未验证风险、服务器记录时间。

- `APPROVED` 表示任务 ACCEPTED，不表示集成、上线或 Goal MET。
- 多人验收按章程汇总；缺席/超时不等于同意。
- 对象/证据失效时本轮 `VOID`，等待重新初审提交。

### 6.3 G3 方向/结构裁决

**个别意见（每位总工一条）**：总工身份、Direction Policy 版本、brief_id/方向包版本、意见（通过 / 要求修改 / 有保留通过）、保留项或修改理由、签署时间。

**整轮裁决（一人一条）**：G3 轮 ID、绑定的 brief/方向包/规则版本、参与的授权总工与意见引用、汇总结论（APPROVED / CHANGES_REQUESTED / WAITING / VOID）、未满足的规则项、服务器记录时间。

- G3 `APPROVED` 表示方向/结构/里程碑可继续，**不改变任务 ACCEPTED 状态**。
- 联合 G3 未达章程条件时只能 `WAITING` 或 `CHANGES_REQUESTED`，不能拼票通过。
- brief 或方向包变化时本轮 `VOID`，重新发简报。

### 6.4 每条驳回理由

| 字段 | 内容 |
|---|---|
| 原因类别 | ImplementationDefect / EvidenceGap / RequirementChange / AcceptanceError / EnvironmentFailure / IntegrationConflict / DirectionConflict |
| 契约依据 | 哪项验收条目或被违反的既定约束 |
| 事实与复现 | 观察方法、输入、环境、证据与对象引用 |
| 期望 / 实际 | 明确差异；体验判断说明真实场景 |
| 可响应整改 | 最小修正、补证或新契约建议 |
| 影响 | 是否阻断当前候选；哪些工作可继续 |

需要实现整改时，老执行权已经关闭；在无 HOLD 且准入成立后，新 Claim 创建新 Attempt/lease/token，先 ACTIVE，再整改补证、重新初审提交。需求变化走新版本，不算同标准实现缺陷。

### 6.5 申诉

争议对象、申诉人（操作者/验收人/总工）、争议理由/证据、是否标准漂移或职责冲突、复核人及回避判断、裁定/纠正引用。申诉不会直接使成果通过；G1/G2/G3 与更正意见都保留。

## 7. 失效与恢复模板

| 字段 | 要求 |
|---|---|
| Invalidation/HOLD ID | 来源决策/契约/授权/证据变化，或 lease 失联 |
| 权威先后 | 新治理代次/对象 revision、服务器记录时间；先提交屏障，再异步通知 |
| 影响对象 | 显式依赖对象、语义影响猜测、尚不确定范围 |
| 阻断动作 | 认领、提交、通过、集成或发布的具体范围 |
| 允许动作 | 状态解释、候选隔离保存、取消、独立授权诊断 |
| 责任与通知 | 谁判断影响，谁响应更新，何时升级 |
| 恢复方案 | 新版本补做、复验、维持原决策、取消或重新认领 |
| 解除依据 | 当前有效授权/版本/证据、无未知副作用；必要人类确认 |

lease 到期后不能用旧续租复活；新认领在核对后签发新 token。恢复旧备份需要新 authority_epoch，并重新核对外部已经发生的动作。

## 8. 集成、发布与目标观察模板

- **集成记录**：协作组、已 G2 验收候选与 G2 裁决引用、目标基线、组合对象、组合验证、冲突/修正、集成责任人、最终纳入基线。
- **发布授权**：精确集成对象、环境、授权人、窗口、操作 ID、权限范围、回滚/补偿、未知结果查询方式。
- **发布事实**：实际版本/环境、外部可核对来源、成功/失败/未知、回滚事实；超时不等同失败。
- **目标观察**：Goal、测量方法与基线、观察窗口、结果 MET/NOT_MET/INCONCLUSIVE、局限、目标责任人判断与后续意图。

非代码成果按契约纳入项目资料即可完成 INTEGRATED；无需虚构一次部署。任务纳入与业务目标达成仍分开。

## 9. 填写示例：列表首屏优化协作组

以下是**一套连贯的纸面样例**，任何“通过”“生效”都只是假设演练，不是真实签字。

### 9.1 Goal 与意图

- Project：P-demo；Goal：G-17。
- Intent：I-17，“大数据量列表首次可用慢”；先澄清不是研发交付慢。
- 基线/目标：在固定演练环境与代表性数据集上，假设 p95 首次可用为 2.4 秒；暂定目标不超过 1.2 秒。要由目标责任人确认测量方法、样本和约束。
- 目标责任人：陈然。非目标：重写系统、引入新缓存服务、改善所有运行场景。
- 诊断：D-170，受限只读/沙箱测量，结论附原始采样与局限；敏感数据不可上传。

### 9.2 Decision D-17/v1

- 状态：演练假设 ACTIVE；真实使用前必须由有权的人批准。
- 选择：在已测场景引入显式分页接口 P/v2；前端接入新契约，保持旧调用方兼容。
- 备选：仅优化前端渲染、引入缓存、暂不改而补观测。依据必须来自诊断，不能只写“模型认为分页好”。
- 风险：R2，公共 API/协作接口变化；无直接生产迁移授权。
- 讨论：陈然（目标）、王五（接口/集成）、张三（后端执行）、李四（前端执行）。
- 批准：陈然与王五，两个不同授权人，分别确认同一版本；此处只是演练角色设置。
- 假设：演练数据可代表首批场景；持续写入时的分页一致性仍需验证。若该假设影响真实需求，则先 HOLD/补充决策，不偷偷扩大适用范围。
- 实施：WP-17，含 T-171、T-172 和组级组合验证。集成责任人王五。

### 9.3 T-171：后端分页

| 契约项 | 演练填法 |
|---|---|
| Contract | C-171/v1；内容 hash 在真实使用时生成，不伪造一个真实摘要 |
| 授权来源 | D-17/v1 的 R2 批准实施范围；小任务不能摆脱父决策约束 |
| 范围 | 接口 P/v2 的分页、过滤、稳定排序与空结果；不引入外部依赖 |
| 非目标 | 未批准的数据模型迁移、生产数据操作、任意扩展接口 |
| A1 | 固定场景下分页/过滤结果符合确认的样例，空页行为明确 |
| A2 | 同一静态数据集的稳定排序/边界页行为可复核；持续写入场景未证则不得宣称全覆盖 |
| A3 | 旧接口调用方兼容；指定关键回归通过 |
| 证据 | 当前候选上的可信接口/回归测试，环境/测试集版本与原始结果 |
| 责任 | 张三监督后端 Runtime 并做 G1 初审；赵六做 G2 验收（不同于张三）；陈然做 G3 方向/结构裁决；Agent 无 G1/G2/G3 资格 |
| 依赖 | D-17/v1 与接口 P/v2 需有效；集成按指定基线 |
| 停止 | 契约不满足真实一致性需求时发挑战；预算/自动返工阈值按章程，不无限重试 |

### 9.4 T-172：前端接入

- Contract C-172/v1，同样引用 D-17/v1 与 P/v2。

### 9.5 一轮 G1 初审、G2 验收与整改

1. 李四合法 Claim → Attempt A-172-1 + lease/token → ACTIVE。
2. 李四的 CLI 产出“候选-a”；李四先做 G1 初审，发现空页证据缺失，**初审退回**，不建立 G2 验收轮。
3. 补齐证据后，李四签署初审 `PA-172-1`，正式提交：固定“候选-a”、记录初审、关闭执行权 → IN_REVIEW。
4. G2 验收人赵六复现 A2 的旧响应覆盖（演练假设候选-a 仍存在该缺陷），G2 意见为 CHANGES_REQUESTED，原因 ImplementationDefect → REWORK。
5. 无 HOLD、旧权利已关闭、准入成立后，原子新 Claim → A-172-2 + 新 lease/token → ACTIVE。
6. 修正并提供新候选“候选-b”及 A2 证据；李四重新初审 `PA-172-2` 后提交，关闭执行权。
7. 赵六逐项判断；演练假设通过 → G2 APPROVED → ACCEPTED。G2 不要求 A-172-2 的旧 lease 继续有效。
8. 如果赵六新增“导出全部结果”，则 RequirementChange 建新契约/任务，不改变 A2 的缺陷事实，也不把新功能算作本轮实现错误。

### 9.6 联合 G3 方向裁决演练

WP-17 的 R2 结构决策设定为联合 G3：陈然与另一位总工分别对“是否引入 P/v3 游标分页”的方向简报签署意见。演练假设陈然“有保留通过”（保留项：持续写入场景仍需观察），另一位“要求修改”（迁移说明缺失）。按章程的必需职责同意规则，整轮结论为 CHANGES_REQUESTED；陈然的保留意见与修改理由都保留，不能把陈然的通过票当作已通过。

注意：这份输入是方向简报（问题、选项、影响、风险、证据指针），**不含 A2 的复现步骤、日志或 diff**；G3 不替 G2 验收 T-172 的实现。

### 9.7 组合与目标

- IR-17 对 T-171 的已 G2 验收候选与 T-172“候选-b”创建组合“组合-c”，绑定真实演练基线和组合验证。

- Goal 保持 OBSERVING，按固定条件采样。若未达成则 NOT_MET 或 INCONCLUSIVE，建立后续诊断；不能因为两个任务都通过就直接 MET。
