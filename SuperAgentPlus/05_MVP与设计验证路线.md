# MVP 边界、设计验证与演进路线

> 本文描述未来如何验证与推进，不是开发承诺、排期或已经执行的系统测试。本次仅交付设计。

## 1. 第一版要证明什么

**两个或更多的人，使用各自工具，能围绕同一项目在明确契约下协作；系统不会把旧上下文、自报完成、重复操作或无人认可的成果当作有效交付。**

第一版不是证明“可以同时拉起一百个 Agent”，也不是证明“AI 能自动代替 G2 验收或 G3 方向裁决”。它应证明：

- 同一个需求不依赖某个人的完整聊天记忆也能被接续。
- 普通工作不被不必要的开工审批拖慢。
- 结构工作不会因为拆成小任务绕过协同批准。
- CLI 操作者能做 G1 初审，独立验收人能做 G2，总工只读方向简报做 G3；三者不会被 Agent 代签。
- 总工上下文里没有 bug 日志/diff/复现；需要细节时走 purpose/TTL 的 detail pack。
- 并发、失联、重试、版本变化不会破坏正式状态。
- 多个通过的子任务最终能在真实项目基线上成立。

## 2. 推荐 MVP 范围

### 2.1 最小可用范围

- 一个组织、一个项目、一个代码仓库、一个权威控制面。
- 少量成员，包含至少两名不同的人，以验证 R2 多人讨论、G1 初审与 G2 验收；另设至少一名 G3 总工。
- 至少一次联合 G3 演练：两名总工对同一方向简报给出意见，验证规则汇总而非拼票；简报不含日志/diff。
- 两类执行工具参与同一契约。人工桥接也算接入验证，但不能宣传已完成自动托管。
- 先支持代码修复、文档/分析成果、一个受批准的跨模块变更。
- 既有仓库、CI、消息与文档工具继续使用；会议先可用外部文档，系统存确认后的决策版本与授权引用。
- 普通 Worker 不获得生产发布权限；第一版可以只演练到测试环境授权发布。

### 2.2 不能后置的可靠性与治理下限

| 首期必须存在 | 原因 |
|---|---|
| 任务契约、基线与决策版本绑定 | 没有它无法判断执行依据是否过期 |
| 身份与有限委派、人类责任主体 | 不把 CLI 当人，不允许 Agent 自行签字 |
| 操作者初审、G2 独立验收、G3 方向裁决与简报规则 | 没有这一层，“AI 说完成”就仍会直接变成有效交付 |
| 原子认领、lease、fencing 与到期/撤销检查 | 并发与失联是小团队也会发生的问题 |
| 命令幂等、未知结果查询、事务状态/审计/Outbox | 响应丢失和发送失败不应制造重复工作 |
| 决策/契约失效屏障 | 不能靠通知“自觉停下”保障正确性 |
| 适合成果的证据准入与可信复核 | 不能先相信模型自报，后面才补信任机制 |
| 结构化驳回、标准变化与申诉区分 | 这是产品核心，不是可选插件 |
| 串行/受控集成与真实组合验证 | 工作副本隔离不消除集成风险 |
| 受限运行、凭据隔离、外部副作用约束 | 任意代码不能获得控制面和发布权 |
| 恢复核对与备份权威代次 | 不能恢复旧数据库后复活旧写权 |

这些性质可以用很小的实现边界实现，不要求首期建设复杂基础设施。**可以推迟丰富功能，不能推迟对“谁有权推进、什么结果可被认可”的定义。**

### 2.3 明确不做

- 人员绩效排名、AI/人类精确贡献百分比、自动薪酬结算。
- 区块链、跨组织多主共识、全球 Worker 市场。
- 所有 CLI 的通用完全自动托管。
- 完整视频会议、复杂实时画板和全功能协作文档。
- 全项目会话无限记忆、未经权限过滤的全局检索。
- 无人批准的架构替换、自动生产迁移与自动高风险发布。
- 为了扩展性先拆一组微服务，或为了复用先绑定一个未经核验的第三方插件。

## 3. 先做设计验证，再决定实施

### 阶段 P0：纸面协作验证（当前设计后的下一步）

拿一个真实但不敏感的项目需求，不写系统代码，由成员按 [工作模板][templates] 走一遍：

意图 → 诊断/讨论 → 契约 → 认领 → 执行 → 操作者初审（G1） → 正式提交与复验 → G2 独立验收 → G3 方向裁决（仅需要时） → 集成判断 → 结果。

人工模拟重复认领、失联、标准变化、审核争议与决策失效。用 [场景推演][scenarios] 做反例，不因主流程顺畅就跳过故障路径。

**退出条件**：

- 团队同意角色、权限、双轴分级与签字边界，包括“谁 G1、谁 G2、谁 G3、是否 `per_delivery_brief`”。
- 一份契约能让未参加原讨论的人正确接手。
- 普通任务与结构任务均有可解释流程；每项阻塞明确解除条件。
- 对审查争议与需求变化有一致处理方式。
- 首批工具的能力清单有实证/未知标记，不再沿用旧对话中的能力断言。

如果纸面上仍不知道谁有权通过、不知道成果按什么判断，就回到契约与章程，而不是先建服务器。

### 阶段 P1：最小可信闭环

未来实施时，仅覆盖一套权威状态、有限任务池、两类节点、不可变候选、G1 初审、G2 验收、G3 方向简报/裁决、组合集成与故障恢复。可以模块化单体实现控制面；运行代码和可信验证保留隔离边界。

**退出条件**：

- 并发认领只产生一个正式执行权；响应丢失重试返回原结果。
- 过期/撤销 lease 即使 token 仍最大也不能执行受控写入；过期不能续租复活。
- 提交固定候选并关闭执行权；返工先新认领，再整改补证、重新初审提交。
- 无初审签署时提交失败；Agent 不能生成 G1/G2/G3 签署。
- 联合 G3 能按章程汇总同一简报/方向包的意见；缺席与超时不被算作通过。
- 版本失效先于通知生效，漏收通知仍被关键门禁阻断。
- 集成基线变化必须复验，发布授权绑定真实组合对象。
- 不可信或错对象证据不能放行；G1/G2 绑定精确候选与证据快照，G3 绑定简报/方向包版本。
- 总工上下文不含日志/diff；detail pack 有 purpose/TTL，不合并回主上下文。
- 崩溃恢复、事件重发、旧备份恢复能解释每个未决任务与副作用。

以上是未来测试的验收要求，不是本次已经证明的能力。

### 阶段 P2：真实团队运行与异构深化

在小范围真实项目中观察协作收益、审核负担和状态质量。逐项提升节点从人工桥接到协议参与、再到受控托管；不强迫所有工具同时达到最高接入等级。

增加依赖图、上下文包、协同文档关联、通知摘要、适度自动诊断与授权受限的结果观察。对精细失效范围不确定时，继续保守 HOLD。

**退出条件**：相对该团队的基线，协作机制没有放大总返工和审核等待；成员可解释自己的任务、责任、阻塞和数据用途；关键任务没有绕过契约的“影子流程”。具体目标值先测基线后约定。

### 阶段 P3：扩展与规模化（有证据再做）

- 拆分项目级服务或读投影，而不是直接多主写入。
- 多仓库协作组、领域治理、复合发布与数据迁移管理。
- 更完整的项目记忆图与决策协作预演。
- 跨组织只交换契约/证据/裁决的受限联邦。
- 可选贡献分析，仅在数据定义、目的限制、解释与申诉成熟后开放。

**启动条件**：有真实规模、边界或协作瓶颈；当前架构无法满足已测需求。没有这些证据，不把“终极形态”当作开发 backlog。

## 4. 部署与嵌入形态的取舍

| 形态 | 优点 | 限制 | 建议 |
|---|---|---|---|
| 单工具内的协作扩展 | 快速验证流程、沿用一个工具的体验 | 容易把项目身份、执行生命周期和治理绑到该工具 | 可作验证入口，不默认作为长期唯一控制面 |
| **独立项目控制服务 + 适配器** | 工具中立，统一正式状态，跨机清晰 | 需设计身份、协议、存储与恢复 | 建议长期架构方向；初期仍保持小而清晰 |
| 多控制域联邦 | 支持组织/数据边界独立 | 授权、验收、版本与外部信任显著复杂 | 暂不实现；先明确共同契约，再谈联邦 |

独立控制服务可以本地、内网或组织托管，不必须公网。最小形态不意味着无备份、无身份或所有进程共用一个有密钥的工作目录。

## 5. 后续应执行的设计/工程验证

| 验证 | 方法 | 必须证明或暴露的点 |
|---|---|---|
| 目标连续性 | 把不同工具的任务链交给未参与讨论的成员 | 能找到原意图、有效决定、非目标与验收对象 |
| 普通工作摩擦 | 演练一个 R1 工作，记录需要人的判断步骤 | 无不必要开工审批；仍有 G1 初审 + G2 验收 + 证据；G3 不介入 |
| 结构变更偷渡 | 把 API 变更写成小 bug 或拆成多项 | 风险依据语义/边界，不按任务标题或代码行数；R2 需要 G3 简报 |
| 多人认领 | 同时 Claim + 响应丢失重试 | 唯一正式租约，同键原结果，同键异载荷冲突 |
| 到期/撤销退权 | 让租约到期但不重新认领；再写入/续租 | 旧最大 token 不足以授权，过期租约不复活 |
| 返工顺序 | G2 驳回、重认领、重新初审与补证 | 老执行权关闭；新权利在新执行前建立 |
| 失效并发 | 决策替换与 G1/G2/G3/集成同时发生 | 权威顺序可解释，旧版本不能在失效后放行 |
| 证据绑定 | 伪造日志、换 commit、改测试策略 | 检测对象不符与不可信来源，暴露未验证内容 |
| 语义集成 | 两项各自绿、组合失败 | 组合候选真实复验；有人负责修正与发布阻断 |
| 崩溃与恢复 | 提交后发送前崩溃、事件乱序、回退备份 | 状态持久、Outbox 去重补发、新 authority epoch |
| 外部结果未知 | 模拟发布超时但实际成功 | 查询事实而不是盲目重试；无查询能力则人工核对 |
| G2 验收体验 | 给验收人完整候选/证据 | 能判断契约条目、未验证风险与历史响应 |
| 总工污染测试 | 只给 direction + brief，夹带 stack trace/日志 | 总工答方向问题；识别并退回操作细节；不逐条分析 |
| 初审缺失 | 让 Agent 直接提交、再尝试 G2 | 提交被拒；G2 轮无法建立 |
| 联合 G3 汇总 | 两人意见不一致、第三人缺席 | 按章程得到整轮结论，缺席不计同意，不拼票 |
| 隐私与越权 | 跨项目访问、恶意附件、Agent 请求签字 | 内容不扩权，身份不伪造，缓存/摘要不扩大权限 |
| 目标未达成 | 子任务通过但真实指标无改善 | Outcome 不自动 MET，能生成新的诊断而非篡改旧记录 |

测试次数、时长、费用与阈值要按真实场景定义。简单演练可以发现逻辑矛盾，但不能证明生产可靠性；故障注入与实测也不能证明覆盖所有未知风险。

## 6. 如何判断这个系统值得继续

建议记录同一团队的前后基线，而不是比较不同人的“任务数”：

- **结果质量**：符合约定目标的交付、上线后回归、关键未验证风险。
- **协作连续性**：接手需要的信息补充、决策误用、失效后的无效工作量。
- **流动效率**：澄清、执行、审核、集成各阶段等待；按原因返工。
- **人类注意力**：判断所需阅读、重复解释、实际审核成本与可行动告警。
- **资源成本**：受限诊断、执行、验证与集成的时间、计算/模型费用。
- **成员体验**：责任是否清晰，审核是否可抗辩，数据用途是否可理解。

阶段目标不是“审核时间越短越好”。若只是让人更快地乱点通过，反而降低质量。真正要验证的是**在不降低交付判断质量的前提下，减少重复说明、错误实施和等待**。

## 7. 建议固定、但仍待用户确认的设计决策

| ID | 建议 | 状态 |
|---|---|---|
| SAP-D01 | 工具中立的项目协作控制平面，不以固定经理或单一模型为核心 | 待确认 |
| SAP-D02 | 模型建议与确定性正式状态分离 | 待确认 |
| SAP-D03 | 清晰度 C 与风险 R 双轴；普通工作免逐单开工审批 | 待确认 |
| SAP-D04 | 交付分三层：G1 操作者初审、G2 独立验收、G3 总工方向/结构/里程碑裁决；总工只看方向简报 | 待确认 |
| SAP-D05 | 契约/决策版本与候选绑定，失效屏障前置 | 待确认 |
| SAP-D06 | Task/Attempt/Review/Release 分离；初审后提交即关闭执行权 | 待确认 |
| SAP-D07 | 原子认领、幂等、lease + fencing + 到期/撤销检查为首期下限 | 待确认 |
| SAP-D08 | 当前状态 + 审计/不可变版本 + Outbox，不必首期完整事件溯源 | 待确认 |
| SAP-D09 | G2 验收后仍需组合集成，发布有独立授权；G3 不替代 G2 | 待确认 |
| SAP-D10 | 绩效、联邦与复杂实时会议均不进入 MVP 核心 | 待确认 |

这些 ID 是本设计的建议索引，不冒充已经经过人类批准的项目决策账本。

## 8. 最值得与你继续讨论的问题

| 优先级 | 问题 | 暂用默认 | 如果不同，哪些设计会改变 |
|---|---|---|---|
| P0 | 第一批服务谁：你个人、小团队、企业，还是开源协作？ | 有共同项目的小团队 | 身份、多人批准、数据边界、部署与服务方式 |
| P0 | “正式交付”粒度是什么：每个任务、协作组还是里程碑？ | R1 任务走 G1+G2；协作组/里程碑另做 G3；内部步骤不逐项签字 | 人类容量、任务拆分与统计定义 |
| P0 | 单人监督 AI 的自验是否允许？哪些风险不允许？ | 只允许显式低风险单人模式；R2 仍需两人；G2 必须不同于执行者；G3 建议他人 | 权限政策与试用范围 |
| P0 | 总工如何产生、谁可授权？联合 G3 的通过条件是全体同意、法定人数还是必需职责同意？ | 由项目章程列出授权名单与规则；默认单人 G3，高风险才联合 | 权限模型、G3 命令与 UI |
| P0 | 总工能否做自己执行成果的 G3？ | 记录双重身份；建议中高风险由他人 G3，低风险可显式 `self_direction_review` | 独立性政策与审计规则 |
| P0 | 项目结构的边界如何定义，谁覆盖必需领域职责？ | 公共接口、数据模型、核心依赖、模块边界按 R2 | 会议与批准规则、执行范围 |
| P0 | 首先纳管哪两种工具？可接受人工桥接吗？ | 不要求第一版全自动托管 | 适配范围、生命周期与运营负担 |
| P0 | 代码、日志、提示词与验证数据允许离开本机/组织吗？ | 最小上传；密钥留在隔离边界外 | 上下文、验证部署与隐私设计 |
| P1 | 系统先接到现有项目平台，还是提供独立工作台？ | 独立语义层，复用既有 Git/CI/文档 | 入口、通知、项目对象映射 |
| P1 | 从 G2 验收到集成/发布，谁有独立责任？ | 明确组级集成人与发布人 | 正式任务末态、发布门禁与事故追溯 |
| P1 | 对停机、数据损失和离线的容忍度是多少？ | 权威不明确时拒绝关键写入 | 数据库、备份、租约和高可用目标 |
| P2 | 未来贡献分析、外部协作的目的与约束是什么？ | 均默认关闭 | 数据保留、法律边界与联邦信任 |

## 9. 下一次设计评审的建议议程

1. 确认一句话定位与首批用户，不先争论框架。
2. 选一个真实“慢”的问题，澄清是交付慢还是运行慢。
3. 用模板共同写出一个 R1 契约和一个 R2 决策，验证它们是否可交给别人。
4. 演练一次驳回、一次需求变化、一次旧版本迟到提交。
5. 确认首期不能绕过的授权与验收边界。
6. 此后再选择嵌入方式、CLI、身份和部署，决定是否进入实现。

**如果只能先做一件事：共同写出一份别人能执行、能验收、知道何时应该停下的工作契约。它比先搭起服务器更能检验这个构想。**
