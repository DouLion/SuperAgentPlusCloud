## 2. 生长原则

1. **一次只长一根主枝。** 每层必须能独立运行、测试、提交和回滚。
2. **先事实对象，再 AI，再界面。** AI 与 UI 不能先于可版本化、可验证的数据对象。
3. **只有一个事实源。** API 文档与 Mock 都从 API Contract 生成，禁止各维护一份。
4. **AI 只给建议。** 约定、模板、契约、任务都必须经人确认才生效。
5. **不为未来规模提前拆服务。** 当前保持模块化单体，直到压测或组织边界证明必须拆。
6. **每层先用 SuperAgentPlusCloud 自身试跑。** 示例项目不是演示假数据，而是真实使用本系统维护本系统。

### T13｜项目制品与接口契约

**目的：** 让“先约定接口，再前后端并行”拥有一个真实、可引用的契约版本，而不是一句自然语言。

**对象：**

```text
Artifact
  artifact_id / project_id / type / name / version / status
  content / digest / source_task_id / source_submission_id
  created_by / created_at / supersedes
```

一期类型：

- `api_contract`：OpenAPI 3.1 核心子集；
- `api_document`：从契约渲染，不独立编辑；
- `mock_definition`：从契约与示例生成；
- `document`、`schema`、`test_report`。

**确定性校验：**

- 禁止 PUT / DELETE；
- 2xx JSON 响应必须具有 `status / message / data`；
- path 采用 kebab-case，字段按项目约定；
- operationId 唯一；
- OpenAPI 引用存在；
- 前端 / 后端任务依赖同一 `api_contract` 版本；
- 联调任务依赖前端 + 后端。

**交付物：**

- Artifact 存储 / API / CLI / 测试；
- Contract 校验器；
- OpenAPI → HTML 文档渲染；
- OpenAPI → Mock 路由；
- 当前项目的一份真实 `/sap-cloud/api/*` 契约作为种子制品。

**不做：** 通用 API 网关、在线 OpenAPI 编辑器、动态代码生成。

**确认点 C13：**

- [ ] 接受 OpenAPI 3.1 作为唯一接口契约格式；
- [ ] 接受 `{status,message,data}` 为示例默认，而不是所有团队硬编码；
- [ ] 接受 Mock 与文档只由契约生成；
- [ ] 确认首期 Mock 是只读开发辅助，不代理真实后端。

### T14｜AI 编排与规范助手

**依赖：T12 + T13。**

**四类助手（职责分开，不做一个万能 Agent）：**

| 助手 | 输入 | 输出（均为未生效草稿） |
|---|---|---|
| 约定整理 | 团队文档、现有约定 | ConventionPack 草稿、冲突与缺口 |
| 契约设计 | 需求、主干、active 约定 | API Contract 草稿、不确定项 |
| 编排 | 需求、约定、模板、制品版本 | 任务 DAG 草稿、角色提示、预期产物 |
| 校验与影响 | 契约/提交/变更 | must 违规、should 提醒、影响候选 |

**强制输出：**

```text
convention_checks[]
workflow_template_id
artifact_refs[]
tasks[]
uncertainties[]
```

**门禁：**

- AI 不得激活约定包；
- AI 不得发布制品；
- AI 不得创建正式任务；
- 信息不足必须返回 uncertainties，不得补全为事实；
- must 违规的草稿不得被采纳，除非人显式记录例外理由。

**确认点 C14：**

- [ ] 是否先只实现 API 契约场景，暂不做通用编排；
- [ ] 谁可以采纳 AI 编排草稿；
- [ ] must 规则是否允许例外，例外由谁确认；
- [ ] 是否允许不同任务选不同模型。

### T15｜契约与制品工作区

**依赖 T13，建议与 T14 同步后半程。**

项目内新增一级导航“契约与制品”：

1. 约定包：规则列表、作用域、版本历史、模板导入；
2. 编排模板：DAG 表/树，节点依赖与产物；
3. API 契约：路径、方法、schema、版本；
4. 文档：契约渲染结果；
5. Mock：operationId、示例、可复制 URL；
6. 校验：must / should / preference 分组；
7. 引用：哪些任务依赖当前契约版本。

**交付标准：**

- 人能从需求详情生成契约草稿、修改、确认；
- 人确认模板后再发布任务；
- 前端/后端任务详情都显示依赖的契约版本；
- 变更契约时能列出受影响任务与提交；
- 示例项目完成一次契约变更 → 前后端复验 → 联调闭环。

**确认点 C15：**

- [ ] 是否允许一期用 JSON textarea 编辑契约，还是必须结构化表单；
- [ ] Mock 是否随 Center 运行，路径固定为 `/sap-cloud/api/mock/:projectId/*`；
- [ ] 契约文档是否需要导出静态文件。

## 4. 后续枝干（暂不开发）

### T16｜团队、身份与授权

触发条件：超过一个团队真实使用，或需要公网部署。

内容：成员、团队、角色、项目授权、API Token、OIDC/LDAP 可选接入、审计可见范围。当前 `confirmed_by` 等字符串字段需要升级为主体引用。

### T17｜通知、队列与运行可靠性

触发条件：出现无人处理、长时间认领、评审积压、并发写冲突。

内容：通知订阅、Outbox、租约/超时、幂等命令、备份恢复、运行指标。未达到瓶颈前不拆微服务。

### T18｜PostgreSQL / MySQL 与部署

触发条件：SQLite 单写者成为瓶颈，或组织要求使用现有数据库运维体系。

优先 PostgreSQL，MySQL 作为第二适配。先抽数据库方言，再加可选驱动；不做在线双写迁移。
