# 06｜中心增强设计：代码归置、模型接入、前端面板

> 本文解决三个问题：Center 没有模型接入、代码需要归置、Center 没有可用界面。
> 设计依据仍是 [03｜总体架构](03_总体架构.md) 与 [04｜详细方案](04_详细方案.md)，不改变核心链。
> 标记：【判断】我的设计选择，可以推翻。

## 1. 现状与差距

| 能力 | 现状 | 差距 |
|---|---|---|
| 核心链 | 需求→评估→决定→任务→认领→提交→评审，已跑通 | 完整 |
| 主干变更与影响 | 已跑通，且强制处置 | 完整 |
| 模型接入 | **完全没有**。评估、拆解、影响分析只能手工填 | 缺 |
| 代码结构 | `store.mjs` 1978 行、`server.mjs` 523 行，全部函数与路由平铺 | 会随功能继续膨胀 |
| 界面 | 只有 CLI | 缺。查一件事要在命令行与数据库之间来回 |

【判断】三个差距的优先级：**模型接入 > 前端面板 > 代码归置**。但代码归置要排在最前做，因为后两者会持续加代码；现在 2000 行、改一处要通读全文的成本已经偏高。

## 2. 代码归置（T7）

### 2.1 目标

按「数据访问 / HTTP / 领域模块」分层，一个文件只负责一件事；新增功能知道该放哪。

### 2.2 Center 目标结构

```text
center/src/
  bin/center.mjs        启动入口
  init-db.mjs           建库脚本
  config.mjs            环境变量集中读取（PORT/HOST/DB/LLM）
  db/
    schema.sql          唯一建表来源
    store.mjs           连接、迁移、重置（openStore/migrate/reset）
    json.mjs            encodeJson/decodeJson/pick/required/codedError/id 生成
    enums.mjs           全部状态与类型枚举
    events.mjs          appendEvent / listEvents
    projects.mjs
    trunk.mjs
    requirements.mjs
    tasks.mjs
    submissions.mjs
    changes.mjs
  http/
    server.mjs          createServer、路由匹配、JSON 收发、错误映射
    routes/
      projects.mjs  trunk.mjs  requirements.mjs
      tasks.mjs  submissions.mjs  changes.mjs
  ai/                   （T8）
  public/               （T9）托管 web/dist 构建产物
```

**兼容策略**：保留 `center/src/store.mjs` 作为**门面**，从 `db/*` 重新导出全部现有函数。这样 78 个测试与现有调用方零改动，重构风险最低；后续新代码直接引用 `db/*`。

### 2.3 Client 目标结构

```text
client/src/
  api.mjs               HTTP 封装
  args.mjs  limits.mjs  help.mjs
  commands/             每命令一个文件（已符合）
  format.mjs            表格/详情输出（从各命令里抽出重复格式化）
```

【判断】Client 目前结构基本合理，只做轻量抽取，不大动。

## 3. 模型接入（T8）

### 3.1 原则：AI 只给建议，不产生已生效状态

这是 [02｜核心概念与原则](02_核心概念与原则.md) §6 的硬要求。落到实现：

- AI 输出一律先落为**建议记录**（评估建议、任务草稿、影响候选），带 `assessor_type='AI'` 或 `draft` 状态；
- 需求状态只在**人做出决定**时推进，不因 AI 写了建议而变成 `assessed`；
- 任务草稿不进任务池，人确认后才批量创建并开放；
- 面板上建议与确认必须视觉可分。

### 3.2  provider

【判断】不绑定任何厂商 SDK，走 OpenAI 兼容的 `POST /chat/completions`，用 Node 内置 `fetch`。零依赖。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `SAP_LLM_BASE_URL` | 空 | 例如 `https://api.deepseek.com` 或本地网关 |
| `SAP_LLM_API_KEY` | 空 | 缺失时 AI 功能不可用 |
| `SAP_LLM_MODEL` | `deepseek-chat` | 模型名 |
| `SAP_LLM_TIMEOUT_MS` | `30000` | 超时 |

未配置时：AI 相关接口返回 503 + `AI_NOT_CONFIGURED`，CLI 给出中文提示；**核心链不受影响**。

### 3.3 三类建议

| 建议 | 输入 | 产出（草稿） | 人确认后 |
|---|---|---|---|
| 评估建议 | 需求原文 + 当前 active 主干条目 | `assessed_level`、`related_item_ids`、`impact_summary`、`uncertainties`、`proposed_action` | 写入 Assessment（assessor_type=AI），人再决定 |
| 任务拆解 | 需求 + 主干 + 已确认范围 | `[{purpose, done_when, scope, non_scope, serves_item_ids}]` | 批量创建任务并开放 |
| 影响候选 | 变更的旧条目 + 在途任务/提交 | `[{target_type, target_id, reason}]` | 登记为影响项（默认 `to_check`） |

### 3.4 提示词要点

- 只喂**当前有效**主干条目，不喂执行日志；
- 要求模型输出 JSON，并强制包含「依据了哪条主干条目」；
- 信息不足时要求返回 `undecided` / `ask`，禁止猜测补全；
- 响应原文与解析结果都留档，解析失败要能看到原文。

### 3.5 接口与命令

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/ai/health` | 是否已配置、模型名 |
| `POST` | `/requirements/:id/advice` | 生成评估建议 |
| `POST` | `/requirements/:id/plan` | 生成任务拆解草稿 |
| `POST` | `/trunk-changes/:id/advice` | 生成影响候选 |

```powershell
sap advise  --requirement <id>      # 查看评估建议
sap plan    --requirement <id>      # 查看任务草稿
sap impacts --change <id>           # 查看影响候选
```

## 4. 前端面板（T9）

### 4.1 形态

【判断】面板独立成 `web/` 工程，用 **Vue 3 + Vite + Element Plus**，组件能复用就不自己写。Center 只负责托管构建产物，不参与前端构建。

```text
web/
  package.json     vue@3 / vite / element-plus / @element-plus/icons-vue / vue-router
  vite.config.js   dev server 代理到 Center
  index.html
  src/
    main.js  App.vue  router.js  api.js
    views/     ProjectList.vue  Dashboard.vue  Trunk.vue
               Requirements.vue  RequirementDetail.vue
               TaskDetail.vue  Changes.vue  Timeline.vue
    components/  TrunkTree.vue  StatusTag.vue  EmptyState.vue
```

【判断】开发期用 Vite dev server 代理到 Center；生产期 `npm run build` 后把 `dist/` 交给 Center 托管，面板与接口共用 8787 端口。

**注意**：`web/` 允许 `npm install` 前端依赖；`center/` 与 `client/` 仍保持零依赖。

### 4.2 页面与优先组件

| 路由 | 页面 | 主要 Element Plus 组件 |
|---|---|---|
| `/projects` | 项目列表 | `el-card`、`el-button`、`el-table` |
| `/project/:id` | 项目驾驶舱 | `el-row`/`el-col`、`el-statistic`、`el-tabs`、`el-empty` |
| `/trunk/:projectId` | 主干条目 | `el-tree`、`el-table`、`el-tag`、`el-dialog` |
| `/requirements/:projectId` | 需求队列 | `el-table`、`el-tag`、`el-drawer` |
| `/requirements/:id` | 需求详情与决定 | `el-descriptions`、`el-steps`、`el-alert`（AI 建议）、`el-form` |
| `/tasks/:projectId` | 任务看板 | `el-table`、`el-select`、`el-tag` |
| `/tasks/:id` | 任务详情 | `el-steps`、`el-timeline`（提交与评审） |
| `/changes/:projectId` | 变更与影响 | `el-steps`、`el-table`（影响项）、`el-tag`、`el-dialog` |
| `/timeline/:projectId` | 事件时间线 | `el-timeline`、`el-input` |

### 4.3 交互要求

- **建议与确认分开**：AI 建议用 `el-alert type="info"` 或独立卡片，标题写明「建议，未生效」，必须点「采纳」才调用写接口；
- **不可用原因可见**：`el-button` 禁用时用 `el-tooltip` 说明缺什么（缺证据、版本过期、已被认领、影响未处置）；
- **状态不只靠颜色**：`el-tag` 同时带文字；
- **可反驳**：评估建议展示「依据条目 X」，允许改等级与关联后再采纳；
- **结果未知不猜**：请求超时用 `ElMessage.error('结果待核对')`，提供「重试」与「查询」；
- **空态与加载态**：统一用 `el-empty` 与 `v-loading`，不要白屏。

### 4.4 接口

复用现有 JSON 路由，不新增 `/api` 前缀。前端 `api.js` 统一封装 `fetch`，处理 409/503 与网络错误。

## 5. 分期

| 层 | 内容 | 完成标志 |
|---|---|---|
| T7 归置 | store 拆分为 `db/*`，server 路由拆分为 `http/routes/*`，`store.mjs` 变门面 | 78 个测试不改一行即通过 |
| T8 模型 | provider + 三类建议 + 接口 + CLI + 未配置降级 | 未配置时核心链不受影响；配置后可拿到建议且不影响需求状态 |
| T9 面板 | 7 个页面 + 建议/确认区分 | 浏览器可完成从提交需求到关闭变更的全流程 |
