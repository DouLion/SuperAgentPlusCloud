# 04｜详细方案

> 本文给出一期可讨论的数据对象、状态和校验规则。它是设计草案，不代表已选定数据库、权限模型或技术栈。概念说明见[02｜核心概念与原则](02_核心概念与原则.md)。

## 1. 设计约束

1. 当前有效主干必须能被唯一定位；历史不得被静默覆盖。
2. AI 建议、用户声明、授权确认和系统状态必须是不同信息。
3. 需求、任务、提交与主干条目之间使用稳定 ID 或引用关联。
4. 状态变化保留事件或版本记录，并标明操作者、时间和理由。
5. 允许信息不足、待验证和探索工作；不以猜测填满字段。
6. 一期采用可人工完成的流程，不假设自动影响分析准确。

以下字段名是概念占位，需根据实现技术调整。

## 2. 项目 Project

```text
project_id
name
purpose                  # 项目目标或目的的简明表述
scope_summary            # 当前已确认的范围摘要
status                   # active / paused / archived
policy_ref               # 权限与确认规则的引用或版本
created_at
created_by
```

项目范围摘要应链接到主干条目，不替代条目本身。归档项目应只读保留历史；删除策略及法律、合同要求另行确定。

## 3. 主干条目 TrunkItem

```text
item_id
project_id
kind                     # goal / scope / capability / business_rule /
                         # interface / data_contract / architecture_decision / other
statement                # 当前决定或约束，简洁且可检验
rationale                # 为什么这样决定；不得只重复 statement
status                   # proposed / active / superseded / retired
valid_from               # 生效时间，可为空表示待定
valid_until               # 失效时间，可为空
relations[]              # 父子、依赖、约束、影响或替代关系
source_refs[]            # 会议记录、文档、需求、提交等引用
created_at / created_by
confirmed_at / confirmed_by
superseded_by            # 可空；关联替代条目
```

### 3.1 规则

- `active` 条目必须有明确确认依据和有效表述。
- `proposed` 条目不可作为已确认前提强制执行；可用于探索或讨论。
- 替代条目不删除旧条目，而以关系和状态保留历史。
- 一个条目可以关联多个条目；不要求严格树形父子结构。
- 对旧决定是否继续适用于历史任务，应由变更记录逐项判断，不因条目状态变化而自动假设所有历史成果失效。

## 4. 需求 Requirement

```text
requirement_id
project_id
author
source_ref               # 提交入口及原始来源
raw_text                 # 提交者原文
attachments[]            # 原始材料引用
claimed_level            # 提交者自报等级，可空
claimed_reason           # 自报理由
final_level              # 决定确认后的最终等级，可空；与自报等级分开留痕
related_item_ids[]       # 提交者认为相关的条目，可空
status                   # submitted / needs_info / assessed /
                         # accepted / rejected / cancelled
created_at
```

原文应保留；后续摘要只能作为辅助字段，不能取代原文。提交者未填等级或关联项不表示低风险，也不应自动导致拒绝。

## 5. 评估与决定 Assessment / Decision

建议把分析过程与最终决定分开，避免“AI 建议”被误读为已批准。

```text
assessment_id
requirement_id
assessed_level           # L0..L4 或 undecided
related_item_ids[]
impact_summary
uncertainties[]
proposed_action           # accept / relevel / ask / reject / investigate
assessor_type            # AI / human / rule
assessor_id
created_at
source_refs[]
```

```text
decision_id
requirement_id
conclusion                # accepted / relevelled / needs_info /
                          # rejected / deferred
final_level               # 若适用
reason
confirmed_by
confirmed_at
policy_ref                # 确认权限所依据的规则版本
assessment_ref
```

- 评估可以有多个版本；新的分析不能抹掉旧分析。
- 决定须由权限规则允许的主体确认，或由明示的自动规则产生。
- 信息不足时使用 `needs_info` 或 `deferred`，不得默认采用最低等级。
- 谁可以发起或确认各等级，由项目政策配置；L0–L4 本身不隐含职务身份。

## 6. 任务 Task

```text
task_id
project_id
requirement_id
serves_item_ids[]         # 服务、验证或可能改变的主干条目，可多项
related_question_id       # 探索任务可关联待决问题
purpose
scope
non_scope
done_when[]               # 可检验的完成条件
acceptance_evidence[]     # 预期证据类型，可空
blocked_by[]              # 前置任务或外部阻塞
status                    # draft / open / claimed / submitted /
                          # rework / accepted / closed / cancelled
created_by
created_at
```

### 6.1 任务规则

- 进入可认领状态前，应有清楚的目标、范围和可检查的完成条件。
- 至少要有主干条目或明确的待决问题作为关联；探索任务允许以待决问题为主。
- `done_when` 应尽量由第三人验证，避免“完成某功能”等不可检验表述。
- 任务拆分应服务于独立推进、并行或验证需要；不为满足流程而过度拆分。
- 允许需求经确认后不产生任务，但要记录原因及决定。

## 7. 认领 Claim

```text
claim_id
task_id
worker_id
claimed_at
released_at
status                    # active / released / completed / expired
```

同一任务的互斥认领应原子完成。一个 Worker 可认领多个任务。是否允许多人共同认领、何时释放长期未动任务，属于一期待定策略；超时释放应保留记录，不应静默删除认领历史。

## 8. 提交 Submission

```text
submission_id
task_id
claim_id
commit_refs[]              # 仓库标识、分支、commit hash；支持多仓库
summary
self_test                  # 测试命令、结果与环境摘要
known_gaps[]
artifacts[]                # 测试报告、文档等引用
submitted_by
submitted_at
```

每次重新提交都创建新记录。`commit_refs` 必须能指向具体版本；只写“已提交”不足以复核。若 Git commit 已存在但 Center 暂时不可用，应允许稍后补录并保留实际提交时间和登记时间（如有差异）。

## 9. 评审 Review

```text
review_id
submission_id
reviewer_id
conclusion                 # confirm / reject / needs_info
criterion_results[]        # 对应 done_when 的逐项结果及证据
reason
self_review                # 是否提交者自审
reviewed_at
```

- `confirm` 表示本次提交满足任务完成条件，不自动批准主干变更。
- `reject` 应指出未满足条件或缺少的证据。
- `needs_info` 用于结论暂不能作出、需要补充信息的情况。
- 是否强制独立评审，由项目政策确定；同一人自审必须明确标记。

## 10. 主干变更与影响记录

主干变更可以由需求提出，也可以由实现或评审中发现的问题触发。

```text
change_id
project_id
trigger_requirement_id
old_item_ids[]
proposed_item_ids[]
reason
impact_assessment
confirmed_by
confirmed_at
effective_at
policy_ref                # 确认权限所依据的规则版本，可空
status                     # proposed / confirmed / in_effect / closed
```

```text
impact_item_id
change_id
target_type                # task / submission / document / test / other
target_id
assessment_status          # to_check / affected / not_affected
resolution                 # continue / adjust / revalidate / obsolete / pending
reason
owner_id
updated_at
```

实现时字段名可调整。重要的是能区分“待检查”与“确认无影响”，且每个受影响对象都有处置结果或明确的未决状态。确认变更后，应创建或更新新条目并保留旧条目历史；不应直接覆盖旧内容。

## 11. 事件与审计记录

最小事件可包括：

```text
project.created
trunk_item.proposed / trunk_item.confirmed / trunk_item.superseded / trunk_item.retired
requirement.submitted / requirement.updated
assessment.created
decision.confirmed
task.created / task.claimed / task.released / task.updated
submission.created
review.confirmed / review.rejected / review.needs_info
change.proposed / change.confirmed / impact_item.updated
```

每个事件至少记录：事件 ID、项目 ID、对象 ID、事件类型、操作者或自动规则、发生时间、记录时间、理由/来源引用及关联对象。对关键确认和状态变更应保留不可静默覆盖的历史。

## 12. 状态推进建议

### 需求

`submitted → needs_info / assessed → accepted / rejected / deferred`

补充信息后可重新评估；旧评估和旧决定保留。取消需求应保留取消者和理由。

### 任务

`draft → open → claimed → submitted → accepted → closed`

未通过评审时：`submitted → rework → claimed`。重新认领前可以由原执行者或其他执行者领取。任务关闭表示本任务流程完成，不等于所有相关主干变更和影响处置均完成。

### 主干变更

`proposed → confirmed → in_effect → closed`

若确认后尚未到生效时间，可保持 `confirmed`；只有达到约定生效条件后才标记为 `in_effect`。具体是否需要延迟生效由项目规则决定。

## 13. 故障与恢复场景

| 场景 | 一期应具备的能力 |
|---|---|
| 需求提交后无人处理 | 可见队列状态和提交时间；允许人工催办或指派 |
| AI 拆解中断 | 草稿与已确认任务区分；未完成草稿不自动发布 |
| Worker 认领后失联 | 可释放或转交，保留原认领及已有提交记录 |
| Git 已提交但 Center 不可用 | 允许事后补录具体 commit，区分提交与登记时间 |
| 评审者暂不可用 | 保持待审状态，不能默认为通过 |
| 主干变更影响在途工作 | 记录逐项待检查和处置状态，未处置项可见 |
| 两人同时修改同一主干条目 | 通过版本冲突或并发检查暴露，不静默覆盖 |

## 14. 尚待项目决定

以下事项不应被本文假定为已解决：

1. L0–L4 的具体量化边界及项目政策中的发起、确认权限。
2. 哪些类型主干变更必须独立评审或多人确认。
3. 条目存储采用文档、结构化数据库或两者结合。
4. 需求是否允许一个变更包含多个互不相关的主干决定。
5. 任务共同认领、长期未活动认领和超时升级的规则。
6. 多仓库项目中项目、仓库和提交引用之间的映射。
7. 源材料访问权限、保留期限及删除/归档要求。
8. 影响清单何时允许关闭，未检查项目如何升级处理。

这些问题可以通过原型和实际项目试跑逐项确定；在确定前应显示为未决，而不是由实现默认决定。
