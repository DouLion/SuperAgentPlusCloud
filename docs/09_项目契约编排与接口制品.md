# 09｜项目契约、编排模板与接口制品

> 本文设计团队约定如何进入 Center、如何辅助 AI 拆解任务，以及如何产出 API 文档与 Mock。
> 它不是把规范写进提示词，而是把规范变成可版本化、可验证、可复用的项目能力。

## 1. 三层模型

### 1.1 约定包（Convention Pack）

团队或项目的长期偏好，例：

- API 命名：路径 kebab-case、字段 camelCase；
- 响应格式：`{status: 1, message: "ok", data: ...}`；
- 方法限制：禁止 PUT/DELETE，用 POST 动作接口代替；
- 代码规范：目录、命名、错误处理、测试要求；
- 接口设计习惯：先契约、后前后端并行、再联调。

约定分两级：

| 级别 | 作用域 | 说明 |
|---|---|---|
| 团队模板 | 可被多个项目导入 | 团队通用约定，修改后不自动覆盖既有项目 |
| 项目约定 | 当前项目 | 导入模板后形成快照，可继续增删改 |

约定有版本和状态：`draft → active → superseded/retired`。AI 只读取 active 约定。

### 1.2 编排模板（Workflow Template）

描述团队喜欢怎样推进某类需求，而不是固定审批流。

首个内置模板 `contract-first-api`：

```text
接口契约设计
  ├─ 前端按契约实现（依赖：契约完成）
  ├─ 后端按契约实现（依赖：契约完成）
  └─ 联调测试（依赖：前端 + 后端）
```

模板节点：

```text
key / title / purpose_template / done_when_template[]
role_hint / depends_on[] / outputs[]
```

项目可以定义多个模板，Center AI 选择或人指定。模板生成的是**任务草稿 DAG**，人采纳后才创建任务。

### 1.3 项目制品（Artifact）

工作过程中形成的、可被后续任务引用的明确产物：

- `api_contract`：结构化接口契约（OpenAPI 子集）；
- `api_document`：由契约渲染的接口文档；
- `mock_definition`：Mock 响应与示例；
- `schema`、`document`、`test_report` 等。

制品有版本、来源任务与内容摘要。前端/后端任务依赖**契约制品版本**，不是依赖一句自然语言约定。

## 2. 核心对象

### ConventionPack

```text
pack_id / name / description / status / version
scope: team | project
project_id?
rules[]: { key, category, title, severity, value, rationale, examples[] }
created_by / created_at / activated_at
supersedes
```

`severity`：`must`（违反即不可发布）/ `should`（AI 提醒）/ `preference`（默认选择）。

### WorkflowTemplate

```text
template_id / name / description / status / version
project_id? / kind
nodes[] / created_by / created_at
```

### Artifact

```text
artifact_id / project_id / type / name / version / status
content(JSON) / source_task_id / source_submission_id
created_by / created_at / supersedes
```

## 3. API 契约的最小结构

采用 OpenAPI 3.1 的核心结构，不另造一套接口格式；项目响应包络作为项目约定与 schemas 表达：

```json
{
  "openapi": "3.1.0",
  "info": {"title": "项目 API", "version": "1.0.0"},
  "paths": {
    "/orders/query": {
      "post": {
        "operationId": "queryOrders",
        "requestBody": {},
        "responses": {
          "200": {
            "content": {"application/json": {"schema": {"$ref": "#/components/schemas/OrderListEnvelope"}}}
          }
        }
      }
    }
  },
  "components": {
    "schemas": {
      "OrderListEnvelope": {
        "type": "object",
        "required": ["status", "message", "data"],
        "properties": {
          "status": {"type": "integer", "const": 1},
          "message": {"type": "string", "example": "ok"},
          "data": {"type": "array", "items": {"$ref": "#/components/schemas/Order"}}
        }
      }
    }
  }
}
```

文档和 Mock 都从同一个契约生成，禁止分别维护三份事实。

## 4. AI 如何使用

Center AI 拆任务时输入：

1. 需求原文；
2. 当前 active 主干；
3. 当前项目 active ConventionPack；
4. 选中的 WorkflowTemplate；
5. 已存在的相关 Artifact 版本。

输出：

```text
convention_checks[]   # 哪些 must/should 规则影响本次编排
workflow_template_id
tasks[]               # 含 depends_on 与 expected_outputs
artifact_drafts[]     # 例如 api_contract 草稿
uncertainties[]
```

AI 不得自行激活契约包、发布制品或创建正式任务；全部先是建议。

## 5. 校验

先实现确定性校验，再用 AI 补语义：

- 禁止方法：遍历 OpenAPI paths，发现 PUT/DELETE → must 违规；
- 响应包络：检查 2xx JSON schema 是否具备 status/message/data；
- 命名：正则检查 path/operationId/字段；
- DAG：检查 depends_on 引用存在且无环；
- 产物依赖：前后端任务必须依赖 api_contract 任务，联调必须依赖前后端。

## 6. 面板

项目内新增「契约与制品」工作区：

- 约定包：规则列表、启用/停用、从团队模板导入、版本历史；
- 编排模板：可视化 DAG（一期用 Element Plus 树/表，不引入图编辑器）；
- API 契约：路径/方法/schema 表格 + 原始 JSON 编辑器（`el-input type=textarea`）；
- 文档：由契约渲染，不独立编辑；
- Mock：按 operationId 选择响应示例，提供可复制 URL（统一位于 `/sap-cloud/api/mock/:projectId/*`）；
- 规则校验：must/should/preference 分组展示。

## 7. 分期

| 层 | 内容 | 完成标志 |
|---|---|---|
| T12 约定与模板 | ConventionPack、WorkflowTemplate 的存储/API/CLI/测试 | 可建立项目约定并生成模板 DAG |
| T13 制品与校验 | Artifact、OpenAPI 校验、文档/Mock | 一个契约同时驱动文档与 Mock | ✅ 已完成 |
| T14 AI 编排 | 单一 `contract_orchestration` 建议 + `orchestrate adopt` | `contract-first-api` 生成契约→前后端→联调 DAG；人工采纳后才落正式对象 | ✅ 已完成 |
| T15 面板 | 契约与制品工作区、示例项目升级 | 浏览器可维护约定、契约、校验与 Mock | ⏳ 未开始 |

### T13 当前实现边界

- `Artifact` 已支持版本、摘要、发布、替代与退役；
- `api_contract` 采用 OpenAPI 3.1，项目 active 约定决定禁止方法、响应包络、path/字段命名规则；
- must 违规阻断发布，should/preference 留在校验结果；
- 接口文档由契约即时渲染，不保存第二份事实；
- Mock 固定在 `/sap-cloud/api/mock/:projectId/*`，只从已发布契约生成，不代理真实后端；
- T14 已实现单一 API 契约编排助手：只生成 `contract_orchestration` 建议；具名人工采纳后创建 draft `api_contract` 与 open 任务；must 违规、未决项、重复采纳均被门禁；
- T15 Web 契约工作区未实现。
