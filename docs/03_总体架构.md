# 03｜总体架构

> 本文描述系统组件、责任边界、核心流程和一期范围。字段与状态定义见[04｜详细方案](04_详细方案.md)。

## 1. 系统组成

```text
┌─────────────────────────────────────────────────────────────┐
│ Center：项目权威记录与协调服务                              │
│ 需求/问题 → 评估建议 → 人员确认 → 任务 → 提交 → 评审         │
│ 主干条目、决定历史、来源引用、影响处置记录                   │
└─────────────────────────────────────────────────────────────┘
       ▲ 提交需求 / 反馈       │ 任务与相关背景       ▲ 结果 / 评审
       │                       ▼                       │
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ Client：任意参与者│   │ Client：执行者    │   │ Client：评审者    │
│ 提出、补充、确认  │   │ 认领、实现、提交  │   │ 检查、确认或打回  │
└──────────────────┘   └──────────────────┘   └──────────────────┘
                                │
                                ▼
                      Git、测试与文档系统
                      提交引用与材料引用
```

图中的 Client 是参与者的动作类别，不要求是三种不同岗位或三种独立软件。一个人可以承担多个动作。是否要求评审者与提交者不同，由项目治理规则决定；若同一人自审，应显式记录。

## 2. 责任边界

### Center 负责

- 维护项目的权威主干记录、状态和变更历史；
- 关联需求、评估、决定、任务、提交和评审；
- 向参与者提供完成任务所需的主干投影和引用材料；
- 支持权限规则、状态校验、并发认领与审计记录；
- 可借助 AI 生成分析或拆解草稿，并把建议与确认结论分开。

Center 不应被理解为单一、永久的模型会话，也不因保存权威记录就自动拥有项目决策权。

### Client 负责

- 提出问题、补充材料或确认被授权的决定；
- 认领任务，在约定范围内实现或调查；
- 提交可定位的成果和自测证据；
- 对评审意见和变更影响作出处理。

### Git 及外部工具负责

- Git 保存代码版本和差异；
- 测试、文档和会议系统保存各自原始材料；
- Center 保存与这些材料的稳定引用及项目决定，不复制所有原始内容。

## 3. 两个相连的工作层

| 层 | 内容 | 变化特征 | 主要控制方式 |
|---|---|---|---|
| 主干层 | 当前有效目标、范围、能力和关键约定 | 变化相对少，影响可能较大 | 记录理由、来源、授权确认和历史 |
| 执行层 | 需求处理、任务、认领、提交、测试与评审 | 变化较快，可试错 | 清楚的范围、完成条件和提交证据 |

两层之间通过引用关联。执行任务应指出它服务、验证或可能改变哪些主干条目。若暂时无法关联，必须说明是探索、待决问题或尚未归类，不能为了满足字段而随意选一个条目。

## 4. 核心流程

### 4.1 普通需求到交付

```text
提出需求或问题
  → Center 收录原文与材料引用
  → 评估其主干关联、影响等级及信息缺口
  → 被授权者确认接受、改级、追问或拒绝
  → 拆成任务并定义范围和可检验的完成条件
  → Client 认领并执行
  → 提交成果（含 Git commit 引用和自测证据）
  → 评审对照完成条件给出确认或打回理由
  → 更新任务状态；若主干被改变，走主干变更记录
```

“提交”不等于“通过”，“通过任务”也不自动等于“主干决定已变更”。这几个状态应分别记录。

### 4.2 主干决定变更

```text
提出变更及理由
  → 关联当前有效条目与来源
  → 评估影响并列出待检查对象
  → 被授权者确认新决定及生效时点
  → 新条目生效，旧条目保留为历史
  → 逐项处置任务、成果、测试、文档等影响对象
```

一期可由人手工列影响对象。系统须支持“待检查、确认无影响、需调整、已处置”等不同状态，不能把空列表当成无影响结论。

## 5. 权威记录与 AI 会话

每个项目有一个逻辑上的权威记录来源。它可以由数据库和文档组成，但必须能明确区分当前有效版本与历史版本。

每次分析或执行只读取相关的工作上下文，例如关联主干条目、已确认决定、必要来源和任务条件。AI 会话可以新建或结束；会话不是权威记录本身。AI 产出的内容在确认之前保存为草稿或建议，不直接覆盖有效状态。

## 6. 一期范围

### 一期要验证

- 单项目的权威主干条目与变更历史；
- 需求提交、信息补充、评估建议及明确的人类确认；
- 任务拆解、任务认领、Git commit 引用、完成条件和提交评审；
- 主干条目与任务、提交、来源材料之间的引用；
- 主干变更的人工影响清单和逐项处置；
- 基本权限、状态校验和“谁在何时做了什么”的记录。

### 一期暂不做

- 会议、即时通讯等入口的自动接入；
- AI 自动批准高影响决定或自动改写有效主干；
- 自动计算完整影响面或复杂依赖图；
- 绩效与贡献排名；
- 完整树形可视化、跨组织或多项目联邦；
- 复杂审批矩阵、全自动派单和实时协同编辑。

## 7. 主要风险与应对

| 风险 | 可能后果 | 一期应对 |
|---|---|---|
| 主干太长、太细 | 记录成为第二份代码库，难以阅读 | 只纳入可影响后续工作的已确认决定 |
| Center/AI 判断不可靠 | 错误结论因“权威系统”外观而被信任 | 显示依据、区分建议与确认、允许反驳和更正 |
| 变更不登记 | 系统退化成普通任务看板 | 变更流程与旧条目关联，逐项记录影响处置 |
| 任务都被强行归类 | 探索工作被错误包装成确定任务 | 支持待决问题和探索任务 |
| 记录负担过高 | 团队绕开系统 | 从少数关键链路开始，按净收益逐步扩展 |
| 权限规则含混 | 定级与签字相互替代 | 分开配置影响等级、发起资格和确认权限 |

## 8. 验证顺序

1. 手工维护一个项目的少量主干条目和来源。
2. 跑通一条需求到任务、提交和评审的链路。
3. 用明显高影响变更验证系统不会只接受提交者自报等级。
4. 加入第二位执行者，验证认领并发和记录可读性。
5. 修改一项已生效约定，手工列出影响对象并逐项处置。
6. 复盘记录成本、漏项和返工变化，再决定自动化范围。
