# 12｜外部工具适配草案（G 枝）

> 状态：**只读适配已实现**；DSH / OpenCode 适配仅本文约定与能力清单，未接入。
> 基线：G 枝已实现事实摄入、证据引用、任务事实关联与 outbox 订阅投递。
> 设计依据：[11｜多 Agent 接入设计](11_多Agent接入设计.md)、[03｜总体架构](03_总体架构.md) §1。

## 1. 边界：适配器只送事实，不作判断

外部系统（Git、CI、工单、聊天工具）能看到的是**发生了什么**，看不到**这件事算不算完成**。因此：

- 适配器只能调用 `POST /sap-cloud/api/integrations/:source/facts` 与只读查询；
- 不得调用 `POST /tasks/:id/submissions` 直接提交成果（那必须由持有有效认领的主体完成）；
- 不得改变任务、提交、制品、约定、契约的任何状态；
- 事实进系统后只是证据，引用它仍然要由人（或持认领的 Agent）决定是否放入提交。

一句话：**Git 说「有一个 commit」，不等于「任务完成」。**

## 2. 主体与凭据

适配器使用 `service` 类型主体：

```text
POST /actors            { type: 'service', display_name: 'git-webhook' }
POST /actors/:id/credentials { label: 'prod-webhook' }
```

- 使用 `Authorization: Bearer <token>`；
- `service` 不受委派约束，但也不能执行任何人类专属动作；
- 人类 token 调用 `integrations/*` 会得到 `400 INTEGRATION_ENDPOINT_HUMAN`，避免人的判断混进系统事实；
- `agent` 类型调用时必须是该项目上有有效委派的主体。

## 3. 事实对象与字段约定

```text
external_facts
  fact_id      fact_
  project_id   必填，必须已存在
  source       git | ci | issue | chat | other
  kind         commit | build | test_run | issue | message
  external_id  外部系统内的稳定 ID（commit sha、build 号、issue 号）
  payload      JSON 对象，原文保留
  actor_id     上报主体
  dedupe_key   source:kind:external_id（唯一）
```

### 3.1 最小载荷约定

| source/kind | 必须包含 | 建议包含 |
|---|---|---|
| `git` / `commit` | `commit_sha`、`ref` | `message`、`author`、`committed_at`、`files_changed` |
| `ci` / `build` | `status` | `url`、`pipeline_id`、`duration_ms`、`branch` |
| `ci` / `test_run` | — | `status`、`total`、`failed`、`report_url` |
| `issue` / `issue` | — | `title`、`state`、`url`、`assignee` |
| `chat` / `message` | — | `channel`、`author`、`text`、`permalink` |

【判断】只强制「没有它就无法判断这条事实是什么」的字段。强制字段越多，适配器越难接；校验越少，垃圾事实越多。当前取值是这两者的折中。

### 3.2 幂等

同一 `source:kind:external_id` 只存一条。重复上报返回首次记录并带 `deduplicated: true`，不新增行、不重复写事件。

这对 Git 尤其重要：webhook 会重投，CI 会重试，适配器不需要自己维护去重表。

## 4. 证据如何进入交付

```text
事实 → 提交引用（external_fact_ids）→ 评审时可核对
     ↘ 任务关联（link-facts）→ 仅记录关联，不改状态
```

- `POST /tasks/:id/submissions` 与 `POST /agent/deliver` 接受 `external_fact_ids`；
- 每个 fact 必须存在且属于同一项目，否则 `400 FACT_NOT_FOUND` / `FACT_PROJECT_MISMATCH`；
- `GET /submissions/:id` 返回 `external_facts` 摘要（source/kind/external_id/summary），不返回完整载荷，避免把大段日志塞进评审界面；
- `POST /tasks/:id/link-facts` 只建立 `task_fact_links`，响应固定带 `note: "外部事实仅为证据，不代表任务完成"`。

## 5. 事件订阅（可选）

外部系统也可以反过来订阅 Center 的事件：

```text
POST /outbox/subscriptions { url, topics: [], secret }
POST /outbox/dispatch
```

- `topics` 为空表示订阅全部；否则按 `event_type` 精确匹配；
- 请求头：`X-SAP-Event: <topic>`，若配置 `secret` 则附带 `X-SAP-Signature: sha256=<hmac>`；
- 至少一次投递，消费端按 `event_id` 去重；
- 失败按 `attempts` 退避，`available_at` 控制下次尝试时间；
- 5 秒超时，慢消费者不会拖住 Center。

## 6. DSH / OpenCode 适配器草案

### 6.1 共同形态

适配器是一个**本地进程**，不是中心服务的一部分：

```text
外部工具（DSH / OpenCode）
        ↕ 本地协议（stdio / socket / 插件钩子）
   适配器进程
        ↕ HTTPS + Bearer
      Center
```

职责：

1. 把工具事件翻译成 `external_facts`（完成、失败、产出文件、测试结果）；
2. 从 `/agent/inbox` 拉取任务，展示在工具界面里；
3. 把工具的产出转成 `POST /agent/deliver`（需持有 claim 与 fencing token）；
4. 定期 `heartbeat`，退出时 `release`。

### 6.2 能力清单（未核验，必须逐版本核对）

| 能力 | 说明 | 当前状态 |
|---|---|---|
| 读取会话事件 | 拿到「完成了什么」的原始信号 | 未知，需按版本核验 |
| 接收外部任务 | 把 Center 任务推入工具界面 | 未知 |
| 取消执行 | Center 撤销租约后工具能停 | 未知；不做承诺 |
| 结构化交付 | 输出 commit/文件/测试结果 | 可能支持，需核验 |
| 后台常驻 | 无界面持续运行 | 未知 |
| 权限隔离 | 工具只拿任务范围凭据 | 需适配器自行实现 |

【判断】表里标「未知」的，一律按不支持处理，先走人工桥接。不要因为某个工具宣称支持就写进文档当事实——这正是 03 文档强调的「异构能力如实登记，可降级」。

### 6.3 降级策略

| 情况 | 降级方式 |
|---|---|
| 工具无法接收任务 | 人工把任务文本贴进工具，产出后用 `sap deliver` 提交 |
| 工具无法上报事件 | 人工用 `sap fact add` 补录 commit / build 事实 |
| 工具不能取消 | 中心只回收租约，工具侧残留进程由人处理；不承诺远端停止 |
| 工具无结构化输出 | 只上报事实，不自动交付；交付由人确认 |

## 7. 不做什么

- 不做「工具一提交就自动完成任务」；
- 不把适配器做成第二个调度器；
- 不假设所有工具都支持同一套能力；
- 不在适配器里保存 Center 的人类凭据。
